# 文档内容写作

## 文件关系先于单页润色

多个页面一起修改时，先确定入口、索引和正文的职责。入口只回答“这是什么、从哪里开始”；索引只安排顺序；正文负责一个可完成的任务。前置页面不要提前展开后续章节的命令，正文也不要重复索引已经给出的路线。

包含实际源码和构建结构的章节，应在第一次展示源码前加入目录树。先用命令查看真实目录和文件名，再决定展示范围；目录树必须从根目录按实际层级自上而下排序，不能凭想象添加文件。同级内容保持真实且稳定的顺序，通常按源码、构建配置、构建脚本、关键生成结果排列。优先使用 `text` 代码块保留树形层级，并在行尾用简短注释说明职责；注释不能依赖空格精确对齐，过长说明移到代码块后。目录树只展示本节需要理解的 `.cpp`、`.h`、CMake 文件、构建脚本、`compile_commands.json` 和可执行文件或库，不展示缓存、日志、对象文件及其他 CMake 杂项。目录树前说明查看它的目的，目录树后直接说明接下来从哪个文件开始。

> 写或改 `.qmd` 正文、标题、代码块和终端命令时阅读本文件；图表、表格、Callout、FAQ 和交叉引用见 `authoring-elements.md`。

## 章节标题与开篇

- 章节标题由 YAML `title:` 提供，不再写同文本的 `# H1`；页面小节从 `##` 开始。
- 较长的 `##` 按“概念 → 操作 → 验证 → 问题排查”拆分为必要的 `###`；短内容不为凑层级增加标题。
- `###` 只用于独立任务、示例、验证或排查流程。只有一两句话的内容并入相邻小节。
- `##` 下只有介绍性列表、短句或两三项并列内容时，不单独创建 `###`；索引页的 `##` 仅承担分组作用。
- 每个小节开头先说明目标，再给解释、操作和判断标准。句子按“目标 → 原因或条件 → 动作 → 结果”推进，使用“因此”“不过”“完成后”等词时，确保前后句确实存在因果、转折或时序关系。
- 标题与首段一体：首句兑现标题承诺（结论或动作），不要用背景信息推迟回答。
- 首页和卡片先说主题与学习结果；不要把 API、命令或完整小节提纲塞进卡片描述。
- 新手必须掌握的内容放正文；规则、风险和易忘内容使用内置 callout。章末保留简短回顾、下一步和必要 FAQ。

## 长章节的骨架

`##` 表示一个可以独立完成的学习任务；当一个任务同时包含概念、多个操作阶段和验证时，才使用 `###` 拆分。推荐按“为什么需要 → 最小示例 → 实际操作 → 验证 → 排查”递进。内容很多时增加有意义的 `##`，不要用空泛标题或大量短小小节填充篇幅。每个小节开头先说明目标，结尾说明结果和下一步。

开发环境说明按“Windows → WSL2 上的 Ubuntu → 编辑器 → 构建工具”展开，保持 Windows、Ubuntu、VS Code 和 CMake 的职责清晰。直接使用具体名称，不使用抽象的环境称呼。

全文应从目标和前置条件开始，经过问题场景、心智模型、最小示例和操作，最后进入验证、排错、练习或迁移与回顾。不要为了“完整”把不影响首次成功运行的工具和命令提前塞进环境章节。

当一次任务涉及 README、索引页和多个章节时，先按章节路线分配内容，再统一标题、术语、命令和链接。前置文件负责入口与范围，章节负责具体任务；不要让每个文件重复介绍同一环境。README 和首页面向读者，只保留入口、最短路径和必要命令；维护规则与详细规划放到对应的 skills、AGENTS 或运维文档。章节应让读者看到可运行结果，再说明完成当前任务所需的规则。

正文只写当前章节能够完成的事情。不要用“解释为什么……”作为标题或目标，除非后文确实提供了对应的完整说明；仅展示操作时，使用“查看、编译、运行、验证”等中性表达。插件配置和随版本变化的编辑器界面不进入入门流程，必要信息通过官方文档链接提供。

## 重构与事实核对

重构默认在原文基础上进行：先读取原文件、相关引用和任务边界，再局部调整结构、表达和衔接。只有用户明确要求，或原结构无法安全修复时，才删除后重新生成。目录、文件名、版本号、命令输出和工程结构等可从磁盘或命令获得的内容，必须先实际获取；无法确认时只写检查方法，不伪造结果。

需要改名、提取或拆分时，先比较新旧文件的职责和关联，再决定保留哪些内容。拆分后同时复核所有相关文件，统一术语、顺序、链接和重复内容；有效信息不得因文件调整而无依据丢失。

## 代码块

使用普通语言围栏 `cpp`、`bash`、`powershell` 或 `cmake`，不写 `{.cpp}` / `{cpp}`。Mermaid 是 Quarto 特殊图表，必须使用 ```` ```{mermaid} ````，不能写成普通的 ```` ```mermaid ```` 代码块。代码块上方用一句正文说明用途；真实仓库示例优先用 `{{< include /code/.../file >}}` 引用。

代码高亮统一使用 GitHub Light / GitHub Dark，唯一配置来源是 `_quarto.yml`。语义颜色交给 Pandoc/Quarto；不要在 CSS 中按字符位置、括号或命令名称覆盖 token。命令与普通输出需要混合展示时使用 `text` 代码块；它不启用语言高亮，但与其他代码块共享字体、行高、边框和复制功能。

标题使用自然语言，不在 `##`、`###` 或卡片标题中放行内代码；命令、文件名、路径、选项、标识符和状态值应在标题下方的正文中使用反引号标记。不要用反引号包住普通概念、整句说明或仅用于强调的词。

代码块中的注释只解释本节重点。重要代码行在对应行正上方使用该语言原生注释；不支持注释的格式不强行插入。复杂原理放在代码块外，避免逐行翻译。注释不引入正文尚未出现的比较对象，也不把未使用的备选配置写进示例。Shell 整份脚本的用途注释放在 shebang 与 `set -euo pipefail` 之间，说明的是文件本身；展示脚本时保留 `set -euo pipefail`，不要删掉。

代码、命令和终端输出统一左对齐并保留源码中的缩进。需要字段对齐时使用表格，不在代码块中用空格拼出表格。正文中的冒号只做简短引出，能用完整句子说明时不要连续堆叠冒号；短命令如 `wsl` 和 `wsl ~` 直接放入正文，不单独占用代码块。命令已经表达清楚时，直接给出命令，例如写“运行 `wsl ~`”，不再改写成“运行带有 `~` 参数的 `wsl ~`”。

## 终端命令约定

### 前置条件、命令与结果

命令前先单独说明执行环境和前置条件。并列条件使用无序列表；有明确先后关系的操作使用有序列表。不要把系统版本、权限要求和命令挤在同一句中。标记为在 Ubuntu 中运行的只读验证命令，先通过 WSL 实际执行，再展示筛选后的关键结果；版本命令优先于仅检查命令位置。

推荐按“先决条件 → 执行命令 → 预期结果 → 下一步”组织内容。代码块前说明用途，代码块后说明成功判据或下一步。标记为在 Ubuntu 中运行的只读验证命令，必须先通过 WSL 实际执行，再展示经过筛选的关键输出；不能凭空补写路径、版本号或成功结果。会改变系统状态的安装命令可以展示，但不在写作过程中重复执行。

纯命令块只包含可复制的命令，不加 `$` 或 `PS>`：

```bash
sudo apt install -y build-essential gdb cmake ninja-build clang clang-tidy clang-format
```

命令与预期输出的演示块使用 `$`，输出紧跟命令；不在块中使用 Markdown 粗体、斜体或星号。性质相近的验证最多展示三组，其余工具用表格或文字说明。

```bash
# cmake：构建系统
$ cmake --version
cmake version 4.2.3
```

多命令块只用于连续操作步骤，命令之间留空行；容易误解、关键或顺序敏感的命令才在上方加一行 shell 注释。

只有一两条、读者可以直接理解的短命令，例如 `wsl` 和 `wsl ~`，直接放进正文句子。需要区分用途、强调执行顺序或方便复制时，才保留代码块。代码块中的每条重要命令都在它的上一行放一条简短的原生注释，注释不写成长段说明。

代码块与 `text` 输出块都左对齐并使用同一套字体、字号、行高、边框和内边距。`text` 只展示命令与关键输出，不启用语言高亮；Bash、PowerShell、C++ 和 CMake 继续使用 GitHub Light / GitHub Dark 的语义高亮。

## 配置文件与 CMake

`CMakeLists.txt`、YAML 和 Dockerfile 等声明式文件，在代码块内部使用其原生注释，注释放在对应语句正上方。CMake 注释优先采用 [CMake 官方中文文档](https://cmake.com.cn/cmake/help/latest)的术语，不复制大段文档。

## 文档类型边界

这套规则的“目标、解释、验证、少重复”原则也适用于 Skill 和 `handbook/`，但它们优先保持短小、可检索和可执行。Skill 与说明文档默认使用段落、表格、编号步骤和代码块，不为凑结构加入图片或 Mermaid；只有复杂分支确实难以用文字表达时才例外，并补充文字结论。README 遵循 GitHub Markdown，可以保留 Actions、许可证徽章和有信息价值的图片；`AGENTS.md` 只保留硬性执行规则。

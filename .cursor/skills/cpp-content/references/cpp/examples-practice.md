# 示例、错误与练习闭环

## 示例递进

同一概念优先使用四步：

1. 最小版本：只保留当前规则需要的代码。
2. 可观察变化：增加一个输入、类型、资源或控制流变化。
3. 错误对照：展示一个常见错误及编译器、运行时或 sanitizer 的信号。
4. 迁移版本：把规则放入更接近工程的函数、头文件或 CMake target。

每一步都给出“发生了什么”和“下一步为什么成立”。不要一次倾倒最终工程，也不要用省略号隐藏读者必须理解的部分。

## 错误示例

错误示例必须标明它是错误示例，并说明触发条件、预期观察结果和修复原则。对于 UB，不承诺某个平台上的具体输出；应使用 sanitizer、断言或最小复现验证。

## 练习设计

练习按难度递进：修改已有程序、补全一个函数、比较两种设计、再迁移到小工程。每道练习说明输入、输出或约束；答案不应引入尚未讲解的核心概念。

## 代码与正文

代码块前说明执行环境和目的，代码块后说明结果、判据和下一步。真实仓库文件优先使用 include；同一段代码不要在正文、目录树和输出块中完整重复。代码注释只解释学习重点，原理和设计取舍放在代码块外。

源码、编译命令、运行输出、流程图和构建目标必须描述同一个行为。修改示例输出或文件名后，逐项核对文档中的输出块、图表标签、文字说明和 CMake 目标；不能保留来自旧示例的结果。

直接编译命令、CMake 目标和构建脚本必须保持标准、警告选项和输出路径一致。修改 `-Wall`、`-Wextra` 或 `-Werror` 后，同步检查章节目标、命令、CMake 文件和成功输出。首次介绍构建规则时，应说明本章实际使用的警告策略，但不加入尚未使用的 sanitizer 或其他高级选项。

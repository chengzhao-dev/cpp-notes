## 总则（文风基调 + 人称）

像朋友带着你做，亲切但不啰嗦：

- **对话感 + 第二人称**：用「你」，允许协作式「我们 / 一起来」带读者动手；避免旁观/权威口吻（本书 / 主流教程 / CI 对齐）。
- **短句、主动、鼓励式收尾**：一句一义；说明学完能做什么。
- **先跑起来**：优先让读者快速得到可运行结果，再补背景与原理；不要一上来堆理论。
- **最少解释在用时**：解释紧贴代码出现处，一句到位；能少说就少说，把深度留给后续小节。
- **克制不端着**：可轻松开场（如「欢迎！」），但不写不实表述、不堆虚词、不预演 `##` 小节、不三处重复。
- **感叹号克制**：正文不用感叹号；仅章末回顾允许一句鼓励式收尾。

人称细则：

- 用「你」不用「您」（中文技术书通例）。
- 用「本章/本节」或协作式「我们/一起来」带读者；避免旁观语气与无信息 filler（禁用词见 `avoid-words.md`）。
- **人称分工**：「你」用于结果与承诺句（你就能、你将拥有、你已经）与对读者的直接指令；「我们」只用于读者正跟着动手的协作动作句；陈述本章要做的事用「本章/本节」作主体。
- **同段不换人称主语**：一段之内「我们…」「你…」不交替；过程陈述句尽量无主语，人称词只出现在承诺与指令处，密度克制。

## 术语与命名

- 英文术语首次出现加中文释义，之后可用英文：RAII（资源获取即初始化）。
- C++ 专有名词保持英文不翻译：RAII、UB、ADL、CRTP、SFINAE、NRVO、ODR、PIMPL。
- 全文译名统一：rvalue→右值、lvalue→左值、forwarding reference→转发引用、value category→值类别。
- 标准库类型/函数保持原名：`std::vector`、`std::move`。
- 译名以 [zh.cppreference.com](https://zh.cppreference.com/) 中文词条为准。
- **标版本**：新特性首次出现标注引入版本，如「概念（`C++20 引入`）」，让读者一眼判断是否属于新内容。
- 书籍名用斜体（如 *C++ Primer*）；官方文档优先内联链接，不裸 URL。
- **同物同名**：同一所指全篇只用一种写法，大小写/缩写变体（wsl/WSL/WSL2）归并成一个正文写法；命令行工具是另一个所指，用行内代码（如 `wsl`），版本语境（`wsl` 版本不低于 2.3.11）也归命令槽；Windows 功能名、官方文档名等固定原文照抄，不算混用。标题是扫读层，工具名用大写纯文本（见 标题命名规范），属写法例外。

## 句式与节奏（现代中文句段标准）

- 短句为主，主动语态，一句一义。
- 单句尽量 ≤20 字；20–40 字须语义明确，过长拆成两句（句号分层，勿用分号硬接）。
- 段落 3–5 行，一段一个中心；长段落拆短。
- **段落句数预算**：引言与正文段落尽量不超过三句；四句以上先合并同类信息（如「是什么」并进「装什么」的推进句）或删去次要句，拆不开再分段。
- **逗号分句要连贯**：「手段 → 结果/目的」关系的两个分句用「让/把/再」等连接词串成一句连贯的话，不停在松散的「A，B。」并列；真正的排比/对仗并列才用逗号分句。例：`装好并启用 WSL2，让 Ubuntu 成为开发环境`。
- **数字用法**：计数、版本号、命令参数用阿拉伯数字（3 个、2.3.11、19041）；修辞概数与习语用汉字（三步、两类、一对）；步骤编号用「第 1 步」。
- 复杂信息用列表/表格，不用长从句堆砌。
- 中文正文用全角标点（，。：；！？「」（））；代码块与内联代码内保持 ASCII。
- **解释冒号改写成正式句子**：用冒号提起解释或展开时，改用句号拆成两句，如「WSL2 是 Windows 里的 Linux 子系统。我们会在其中装好 Ubuntu」。保留三类冒号：标签后（**标签**：、第 X 步：）、引出列表与命令块（命令如下：）、注意块头（注意：）；「看 X 判断状态：A 表示…」属标签枚举，保留。示例见 cases/long-sentence.md「少用解释冒号硬接」。
- **陈述句不带吞吐尾注**：「默认情况下，X 使用 Y」一句收住事实；「一般不用改」「通常没问题」这类评价尾注不挂在事实句末尾——或删，或并入注意块。
- 的/地/得 用法正确；**禁用 / 空泛措辞见 `avoid-words.md`**（冗余虚词、空泛动词、旁观 filler 等）；介词准确（「在 Windows 上」非「在 Windows 内」）。
- 列表（bullet）的中心结构见下文专节「列表（bullet）的中心结构」，以「首句点题 → 依次推进 → 末尾呼应」三步取代按类型硬定开头风格的旧法。

### 分号（；）的克制使用

正文里分号（；）只在**排比/对仗的并列项**之间使用；普通转折、补充、因果用逗号（，）或句号（。）断开，不要把分号当短句号用。这条是「长难句拆解」的配套规则，能拆成两句就拆，不必用 `；` 硬接（亦见 句式与节奏 的「勿用分号硬接」）。

- 排比可用：三个及以上结构相近的并列分句，用 ；分隔更紧凑，如「先装环境；再配工具；最后验证」。
- 非排比不用：两个平列但结构不同的句子，直接拆成两句用 。，或用 ，衔接。避免「……发行版；本节只演示……」。

> 示例见 cases/semicolon.md
> **关联**：并列 bullet 的排比分号见 列表（bullet）的中心结构（动词起头写法的 `；` 收尾）；路线图引导句也遵循此克制（见 路线图（引导句 + mermaid）的中心结构）。

### 括号（（））的克制使用

正文里的括号补充说明一律改写成正式句子：括号内容与句子同等重要就用逗号衔接或独立成句；只是可删的细节直接删去。两类紧凑场合允许保留：表格标签、代码注释等对照式括号（如 运行中（Running））；两法对比与条件标注的推荐级括号（如 方法 2：一步迁移（需 `wsl` 2.3.11+，推荐）、环境变量（快速上手））。

> 示例见 cases/parentheses.md
> **关联**：解释内容按 长句三步 融入句子（见 长难句）；标题一律不加括号（见 标题命名规范，比正文更严格）；与 分号（；）的克制使用 同属标点克制系列。

## 常用句式库

以下句式为常用范式，写作时按场景取用贴合的一条，**每处只取一条、不堆砌**；与本书其他规则冲突时以更具体的规则为准。

- **是句 + 它句（章首开头范式）**：术语定义独立成句，后句用「它/在它上面」承接展开，不把解释用括号塞进首句。例：「OpenCode 是一个开源的 AI 编码代理。它提供终端界面、桌面应用和 IDE 扩展等多种使用方式。」
- **是句 + 非限定定语从句**：一句定义 + 「，这些…」补充特性。例：「OpenCode Zen 是由 OpenCode 团队提供的模型列表，这些模型已经过测试和验证，能够与 OpenCode 良好配合使用。」
- **并列动词串行 + 或者收尾**：三个可选动作用逗号串行、末项用「或者」。例：「可以从多个内置主题中进行选择，使用能自动适配终端主题的主题，或者定义您自己的自定义主题。」仅用于**可选**并列；本章时序推进仍用「先…再…」。
- **对比切入**：引出与常见做法不同的设计。例：「与使用固定颜色的传统主题不同，system 主题具有以下特点：」
- **默认情况句式**：先讲默认行为，再讲例外；默认句一句收住，例外句用「再/才」衔接（「默认情况下，X。…时，再 Y」）。例：「默认情况下，OpenCode 使用我们自己的 opencode 主题。」
- **收益句**：动作/设计之后接「这可以避免…」「这有助于…」。例：「OpenCode 的大多数快捷键使用 leader（前导键）。这可以避免与终端中的其他快捷键冲突。」
- **不必…但建议…**：让步 + 推荐。例：「您不一定需要使用前导键来设置快捷键，但我们建议您这样做。」
- **条件推荐**：例：「如需项目级别或持久化的配置，请使用 opencode.json。」
- **限制 + 变通 + 标注推荐**：例：「虽然 opencode 不会自动解析文件引用，但您可以通过以下两种方式实现类似的功能」+「推荐的方式是使用 opencode.json 中的 instructions 字段」。
- **比较式推荐**：例：「使用 opencode.json 配合 glob 模式（如 packages/*/AGENTS.md）比手动指定指令更易于维护。」
- **有用性句**：说明适用时机。例：「这在创建需要与终端配色方案无缝融合的主题时特别有用。」「当您希望阻止某些提供商被加载时，此选项非常有用。」
- **推论句**：列表/规则后收一条推论。例：「这意味着项目配置可以覆盖全局默认值。」
- **具体值推演**：给一组具体值走完流程。例：「例如，如果您的全局配置设置了 autoupdate: true，而您的项目配置设置了 model: "…"，则最终配置将包含这两个设置。」仅用于专门讲解具体知识点（同「一般段落不举例如」的适用范围）。
- **格式规范句**：例：「模型应按如下方式引用：`<providerId>/<modelId>`」+ 示例清单。
- **类比句**：例：「可以把它当作团队中的一名初级开发者来沟通。」
- **假设叙事**：例：「假设你让 OpenCode 做了一些修改。但你发现结果不是你想要的。」
- **时间链**：步骤显式衔接。例：「导航到你想要处理的项目目录。再运行 OpenCode。接下来，运行以下命令为项目初始化。」
- **问题式引导**：例：「没有看到你想要的提供商？欢迎提交 PR。」
- **一次性设置句**：配置/初始化步骤用「只需一次 + 升级保留 + 随时可改」安顿读者。例：「每台计算机上只需要配置一次，程序升级时会保留配置信息。你可以在任何时候再次通过运行命令来修改它们。」
- **分层覆盖句**：机制句 + 「所以」实例句。例：「每一个级别覆盖上一级别的配置，所以 `.git/config` 的配置变量会覆盖 `/etc/gitconfig` 中的配置变量。」
- **习惯句**：趁早做 X，以免 Y。例：「要养成一开始就设置好 `.gitignore` 文件的习惯，以免将来误提交这类无用的文件。」
- **迁移视角句**：面向有其他语言/工具背景的读者映射行为差异。例：「不像其他 VCS 系统，Git 并不显式跟踪文件移动操作。」

## 长难句的中心结构（当句子必须长时）

一段话若无法拆短（如章节引言要同时交代动机、手段、结果），用「三步」结构保住中心，避免散成并列从句：

- **首句点题**：首句点明本段唯一中心，后续所有从句都服务它。
- **依次推进**：中部长句不堆并列，而按「先…再…；…之后」的自然时序一步推一步，每步朝同一方向。
- **末尾呼应**：末句回到开头的承诺/目标，长句再长也不散。
- **解释/补说少用破折号 `——`**：追加说明、同位解释用逗号（，）或句号（。）断开，不要把 `——` 当「硬接」工具；能拆成两句就拆（与「分号克制」同源）。
- **合并的边界**：三步合并只适用于同一命题的时序推进；一句里装着两类不同信息（事实 + 方法、现象 + 对策）时，改用短列表拆开、每条一句，不硬合成长句。

> 示例见 cases/long-sentence.md

> **关联**：能拆成两句就别用 ；硬接（见 分号（；）的克制使用）；三步同样用于 列表 bullet（见 列表（bullet）的中心结构）与 路线图引导句（见 路线图（引导句 + mermaid）的中心结构）；段落级重复先合并再用三步（见 相邻段落（内容重复 / 接近时合并））。

## 段落组织

### 相邻段落（内容重复 / 接近时合并）

上下两个段落若讲同一件事、或内容重合度很高（同主语、同落点、只差一句细节），不要各写一段，先梳理核心、再按「长句三步」合成一段输出。两段都写一遍，读者读到第二遍才拿到结论，是冗余。

- **先梳理核心**：把两段共同要传达的一点拎出来（通常是「看 X 判断状态 → 据此做 Y」这类单一命题），丢弃各自重复的表达。
- **再用长句三步合成一段**：首句点题（首句点明合并后的中心）→ 依次推进（原两段的差异点用对仗/分号并列）→ 末尾呼应（落到下一步，如「命令如下：」）。
- **合并时只保留关键部分**：去同存异后只留关键信息（方法怎么做、落到什么动作），示例路径、「例如」举例、兼容性注脚等次要细节一律不带入；需要展开的细节由紧随其后的代码块或专门小节承载（见 详略与衔接）。
- **隔块两段各一句**：两段被输出块/代码块隔开且讲同一件事（前段引出、后段读结果）时，各压成一句；后段不重复前段已点题的框架。
- **邻近的并列 bullet 同样适用**：见 列表（bullet）的中心结构 与 列表项要短，长内容改表格；段落级重复与列表级重复同理，都是「去重后合一」。

> 示例见 cases/adjacent-paragraphs.md

> **关联**：合并后的单段仍按 长句三步（见 长难句）写；对仗处用 分号（；）的克制使用（见 分号）；与 去重与主题聚焦 的「近邻不重复」同源，是段落级特例。

### 详略与衔接（该清楚则清楚，该模糊则模糊）

递进的内容前后要接得上：出现新方法、新术语时，先用一句话说清它是什么、怎么做，再往下走；一般叙述该模糊处就收住，不堆细节与例子，问题的对象与条件直接说出来。

- **术语先解释再用**：新方法先用一句话说清做法，不甩一个读者不懂的说法。反面：「兼容性最好的是导出再导入，可在任意 WSL2 版本间迁移」——读者不知道「导出再导入」是什么；正面：就地写成「先导出成备份文件，再导入到新位置」。
- **直陈问题，不拿示例指代**：说清问题的对象与条件（什么软件、装在哪、什么状况），不用「C 盘紧张 → 迁到 D 盘」这类示例字母代替陈述；具体盘符、路径留给命令与输出。反面：「C 盘空间紧张时，可整体迁移到 D 盘」；正面：「系统盘空间不足时，可把 Ubuntu 整体迁移到其他磁盘」。
- **一般段落不举「如/例如」例子**：举例是专门讲某个具体知识点时的展开手段（如解读 `<distro>` 占位符时给出 `Ubuntu-24.04`、挑最常用的 `g++` 与 `cmake` 演示验证）；普通叙述把「例如迁到 X」收成「到其他磁盘」，具体值交给代码块。
- **衔接突兀即重写**：前后段明显递进，中间却冒出没铺垫的概念或跳步的因果，读者就会卡住；按「问题 → 方法（就地说清）→ 动作」重排，该说清楚说清楚，该模糊处收住。
- **动作链写完整**：重启、注销、等待这类间接步骤之后，写明下一个要做的动作（如「重启电脑后再运行一次 `wsl --install`」），不用「再试」「再看看」这类模糊收尾。
- **权威出处已承载的操作不转抄**：换源、安装等步骤若已有权威页面详细承载（清华镜像帮助页、官方文档），正文只写决策（何时需要）+ 出处链接（「做法以 X 为准」），不转抄会随版本漂移的具体步骤。
- **因人而异的路径不进正文**：路径含用户名等每台机器不同的部分（如 /home/<用户名>）时，正文用语义指代（「Linux 主目录」），具体值由命令语义（`~`）承载；这类路径读者无法核对，写出像要逐字确认。
- **前向引用一句带过**：后文专章细讲的内容，一句预告 + 当下够用的最小解释（「链接的完整过程会在后面的章节中详细介绍，这里只需要知道它把库函数的实现接到你的程序上」），不当下展开细节冲淡主线。

> **关联**：合并段落只留关键部分（见 相邻段落）；括号补充、内联代码密度、示例指代同属信息密度克制（见 括号（（））的克制使用、代码与正文分工）；与 去重与主题聚焦（具体化）互补——该具体处（环境名）直呼，该模糊处收住。

### 对比型知识点（相似概念先分家）

两个功能相似、容易混淆的语言概念（`new` vs `malloc`、`std::move` vs `std::copy`），用「差异设问 + 双条结论 + 代码」三段开场，不写一段纠缠异同的长文。

- **差异设问开场**：先承认两者功能相似、容易混淆，再点出「但两者在 X 上有较大不同」，给读者一个分家的问题意识。
- **双条结论列表**：无序列表各给一句结论（「A 的作用是…；B 的作用是…」），一句收住，不展开。
- **代码随后印证**：结论列表后紧跟示例代码印证差异；同一目标的两种做法（方法对比）不走此范式，见 延伸内容环节 的方法标注。

## 列表（bullet）的中心结构

列表与长难句同理：一组信息用「三步」保住中心。把长句三步映射到 bullet 列表：

- **首句点题（引导句）**：列表前的引导句须是单一命题，点明本组 bullets 的共同中心（如「学完本章，你就能：」），不用无意义标签（「以下是目标：」）。
- **依次推进（条目顺序）**：bullets 按章节逻辑时序排列（先…再…终…），一步推一步朝同一方向；**不要求句式整齐划一**，每条按自身内容选最顺的写法（见下「条目开头写法」）。
- **末尾呼应（末条或尾句）**：末条回到引导句的承诺；若末条仍是中间步骤，可在列表后加一句收尾，把「你就能…」落地。

### 条目开头写法（按内容选，不写死一种）

- **动词起头（默认）**：bullet 是干净的原子成果/动作时，动词领衔。例：`装好并启用 WSL2，让 Ubuntu 成为开发环境；`
- **环境状语前置**：描述「在某个已点名的环境里做某事」时，把「在…环境里」前置作状语再接动词，避免动词后拖长地点补语导致拗口。例：`在 WSL2 Ubuntu 环境里装好并验证 C++ 构建工具链`（对比拗口写法：`装好并验证 C++ 构建工具链，就在 WSL2 Ubuntu 环境里，默认…`）。
- **细节下沉**：bullet 还带默认/条件等次要说明时，下沉到正文小节，保持列表项主干干净，同时遵循「具体化」原则（见去重与主题聚焦）直呼环境名。例：目标列表只写「在 WSL2 Ubuntu 环境里装好并验证 C++ 构建工具链；」，源细节（默认官方源、偏慢换镜像）下沉到 `### 软件源` 小节，且该节本就在装工具链之前讲解，语境顺序正确。
- **名词标签加粗**：bullet 是「名词标签 + 说明」的名词定义/分类类列表（如先决条件、组件说明）时，加粗名词标签，说明跟在冒号后。例：`1. **操作系统**：Windows 10 版本 2004 及以上，或 Windows 11；` / `2. **CPU 虚拟化**：已在 BIOS/UEFI 中开启。`

### 列表项要短，长内容改表格

列表是「要点清单」，不是段落。bullet 内只放一句短语/短句，不要把长说明塞进列表项（一级或二级都一样）：

- **二级列表允许**：`-` 下再 `-` 用于细分（如「状态 → 该状态的命令」）是合法结构，但二级项同样要短，不写长句。
- **长说明移出列表**：某项若需要一整句以上的解释，改为正文段落，或改用表格。
- **成对信息用表格**：当多条并列项都是「名称/命令 — 作用」「状态 — 命令」这类成对结构时，优先用表格而非列表；表格比列表更利于扫读。
- **表格单元格也只放短语/短句**：单元格里不写长句；过长的说明放到表格外的 note（如 `>` 引用块）或正文。
- **表格加「适用状态」列**：若命令/操作依赖前置状态（如 WSL2 的 `Running`/`Stopped`），用「适用状态」列标明该指令在哪个阶段使用，与「作用」列维度不同（何时用 vs 做什么），不冲突。

> 示例见 cases/list.md

> **关联**：bullet 内部遵循 长难句短句/三步（见 长难句）；并列项用 排比分号收尾时见 分号（；）的克制使用；标签/节点文案点名环境见 去重与主题聚焦（具体化）。

### 参考文档体的列表形态

参考文档常见的信息组织形态，按场景取用；正文列表注解一律用「：」或改表格，`code - 说明` 形态仅在本节清单中使用：

- **可用选项清单**：JSON/配置块后用「可用选项：」引导，每条 `key - 说明（默认值：3）。如果…，则忽略此选项。`；默认值标注统一「（默认值：…）」或「（默认为 …）」。
- **目录内容清单**：「该目录包含：`auth.json` - 身份验证数据，如 API 密钥、OAuth Token」——`code - 说明，如 X、Y`，用「如」字举例。
- **优先级顺序列表**：编号项「名称（来源）- 用途」，列表前一句「后面的源覆盖前面的源」，列表后接推论句「这意味着…」。
- **平台分支列表**：路径/操作按平台分条，「macOS/Linux: ~/.config/…」「Windows: 按 WIN+R 并粘贴 …」——标签 + 路径或动作。
- **条件行为列表**：「当某个提供商被禁用时：即使设置了环境变量，也不会被加载。」——「即使…也不会…」排比，列出某状态的全部后果。
- **路径/位置清单**：「将它们放在：全局：~/.config/… 项目级：.opencode/…」——用途标签 + 路径。
- **三档清单**：同类工具/选项按强度排：`name（默认）- 快速响应，适合简单任务` / `… - 性能均衡，适合大多数工作流` / `… - 最强大，适合复杂分析`。
- **两法对比标注**：「使用以下方法之一迁移：」引出，各方法用加粗标签 + 括号标注推荐级：「方法 1：导出再导入（通用）」「方法 2：一步迁移（需 `wsl` 2.3.11+，推荐）」；优先级提示（如「配置文件中的选项优先级高于环境变量」）用 `>` 或段末一句。
- **标题强度前缀**：进阶小节用「进阶：」前缀；高风险操作标注「（最后手段）」。

## 路线图（引导句 + mermaid）的中心结构

章节开篇用「目标列表 + 路线图」成对呈现（见 AGENTS.md / basics.md）：目标列表列**成果**（学完能得到什么），路线图（mermaid）画**路径**（怎么做）。两者目的不同，不重复；路线图可承载目标列表省略的过程细节。

- **引导句衔接**：mermaid 前的引导句须把图与目标列表扣起来，用「先…再…」呼应依次推进，一句完成「点题路线 → 推进 → 指图」，例如「本章的路线是先装好 WSL2 与 Ubuntu，再在它里面装好并验证 C++ 构建工具链，下图就是这条路线」。不用冒号引出展开。不预演 `##` 小节、不另起炉灶。
- **图下默认不加说明**：节点文案自明；仅当分支需要指引时，在图后补一句「分支 X 在『Y』小节展开」，不重复节点内容。
- **节点文案对齐目标列表**：图内节点用词与目标列表逐一对齐（如「装好并启用 WSL2」「用 Ubuntu 作为开发环境」「安装并验证 C++ 构建工具链」），验证合并进对应节点，不各写一套。
- **分支对称 / 细节下沉**：条件分支（如网速慢换源）两条路径详略须一致，不比默认路径更啰嗦；具体步骤下沉到对应正文小节（如 `### 软件源`），路线图只点方向。
- **技术约束**：mermaid 用 ```` ```{mermaid} ```` 带花括号围栏（语法见 `../quarto/authoring.md`），
  块首行加 `%%{init}%%` 指令（字体栈 + `wrappingWidth: 320`，写法见 authoring.md「图表」）；
  节点/边文案用中文，节点文案尽量 ≤18 个汉字保持单行，超长才换行。

## 链接（正文中的 URL）的写法

正文里的外部链接统一内联、用描述性文字承载，不把裸网址甩在句尾（即把链接直接裹进文字，让可见文字承担句子成分）：

- **不裸露 URL**：正文不出现裸链接（`<https://...>` 或 `https://...` 原文），裸链接既难读又打断节奏。
- **内联描述性链接**：用 Markdown 内联 `[可见文字](URL)`，可见文字须是**有意义的描述**（如「WSL 官方文档」「清华镜像帮助页」），不用「这里」「点击」「详情」或原 URL 当文字。
- **链接文字即句子成分**：让可见文字承担主语/宾语，自然嵌进句子，如「更多安装选项与排错请看 [WSL 官方文档](URL)」，而非「详见 <URL>」。
- **字面 URL 才用代码格式**：当 URL 本身是配置值/数据（如 `sources.list` 里的 `http://archive.ubuntu.com/ubuntu`），用反引号代码格式呈现，不必做成可点链接。
- **外部参考归并到「相关资源」**：章末多个外部链接统一放进「相关资源」列表（已是内联链接），正文只留最必要的一处。
- **内部资源用相对路径**：站点内资源引用相对路径，不写死 `https://...` 绝对 URL（见 `../quarto/pitfalls.md`）。

> **关联**：链接文字作为句子成分时，仍受 长难句短句 与 分号克制 约束（见对应节）。

## 中英混排空格（盘古之白）

中文与英文/数字/内联代码/链接之间要加半角空格（"盘古之白"），让 CJK 与拉丁字母清晰分隔；全角标点前后不加空格。

- **CJK ↔ 拉丁字母/数字**：两侧加半角空格。例：「在 Windows 上用 WSL2 搭一套 Linux 环境」「装好后在 PowerShell 中用 `wsl --status` 确认」「至少需要 2 GB 内存」。
- **CJK ↔ 内联代码**：内联代码视为拉丁内容，两侧加空格。例：「运行 `wsl` 或直接打开 Ubuntu 应用」「编辑 `/etc/wsl.conf`」。
- **CJK ↔ 链接**：看链接**可见文字**的首字符语种，不在标签上判断：
  - 可见文字以拉丁开头（如产品名 `WezTerm`、含英文的「[WSL 官方文档](URL)」）→ 前加空格：「更多安装选项与排错请看 [WSL 官方文档](URL)。」
  - 可见文字是中文 → 紧贴中文、**不加**空格：「做法以[清华镜像帮助页](URL)为准」。
- **全角标点前后不加空格**：，。：；！？「」（）两侧不留空；英文短语若用 ASCII 括号 `(WSL)`，括号**外侧**加空格、内侧紧贴（「Windows Subsystem for Linux (WSL)」）。
- **强调标签内的中英空格跟随其内文本字符的语种**，不看标签本身；`<strong>`/`<em>` 外侧与中文之间照常加空格。
- 例外：表格单元格、代码块、YAML 内照常不强制；代码块与内联代码内保持 ASCII 标点不变（见 代码块约定）。

## 正文强调（strong / em）

- **句内关键词/按键强调**用 `<strong>`：「再次按 <strong>Tab</strong> 键」「你<strong>可以使用</strong> <code>/undo</code> 命令」，加粗文本与中文之间照常加空格。
- **界面元素体例**：导航路径整链写成「A → B → C」，层级名与按钮名用「」包裹；菜单与选项名保持原文不翻译。例：「控制面板 → 程序 → 启用或关闭 Windows 功能」。
- **列表项的小标题（条目标题）用加粗独立段**承载：li 内先写一段加粗文字作条目标题，其后跟说明段/代码块/提示框，不把条目标题写成嵌套标题。例：

  ```markdown
  - **使用 Node.js**

    安装命令说明……（`npm install -g opencode-ai`）
  ```

- **术语/概念**用 `<em>`（非用户操作的概念，如「<em>计划模式</em>」）；用户操作/强调用 `<strong>`。
- 加粗/强调内的中英混排空格同样遵循上一节规则。

## 代码与正文分工

- 代码块保持高对比正文色，**不要**给代码涂灰（见 `theme/css/code.css`）。
- 代码上方用一句「说明段」写做什么；代码下方可放「输出块」展示预期结果。
- **代码后逐项解读**：块后需解读多个产出、分支或条件时，用编号列表逐条对应（项首带代码名/变量名），不用长段复述；解读点只有单个时留在正文句子。
- **失败路径预判**：成功验证后随文补一句常见误区（「如果在 PowerShell 里直接运行 `g++` 提示找不到命令，多半是…」）；高频、当场会踩的紧贴验证步骤写，低频、多成因的才收进「常见问题」。
- **设疑揭示（反直觉现象）**：演示反直觉现象按四拍走——命令/输出 → 一句问句点破（「怎么回事？文件怎么同时出现在两个区？」）→ 揭示机制一句 → 落到正确做法一句；比单纯失败预判更深一层，适合作错觉演示（迭代器失效、隐式转换、UB 现象）。
- **读输出提示再行动**：CLI 输出自带下一步提示时指给读者（「输出已经提示了怎么做，按提示运行」），先读输出再敲命令；不替读者把提示抄成新步骤。
- **验证判据句式**：验证步骤先给通用判据（「运行 X，输出首行打印出版本号，就说明这个工具可用」），再挑最常用的代表工具演示，尾句交代其余工具同理（「需要用哪个，就运行哪个的 `--version`」）；不为每个工具逐个建块；多个代表工具的演示合并到一个演示块、注释区分身份（块结构见 `../quarto/authoring.md`）。
- 行内代码用反引号；行内代码与占位符只用 ASCII（`<distro>`），中文说明写在反引号外。
- **内联代码密度**：一句话或一段内联代码不超过 2～3 枚，多枚连排读起来像一排按钮。首次出现的命令、路径、文件名保留反引号；重复提及或纯语境指代转为正文；枚举过多改用代码块或列表。
- **说明段不抄输出**：预期输出块已展示具体值时，说明只写「运行什么、看到这类输出即成功」，不把输出值抄进正文。
- **状态值/列名用正文**：命令输出里的枚举值与列名（Running、Stopped、STATE）不是可执行代码，用正文写法；命令、路径、文件名、配置键仍用反引号。
- 命令在即将执行的步骤首次出现：先讲「这一步做什么、为何要某前置」，再给命令；**不要**在读者未接触该命令的位置提前引用。
- **命令引导动词统一用「运行」**：单条命令「运行 X」，多条序列「按顺序运行」；「执行」只留给症状描述等非引导场合（如「命令执行失败」），不与「运行」混用。

## 标题命名规范（正文 + 卡片）

所有标题——章 YAML `title`、页面内 `##`/`###`、首页 landing-card——共用下列通用原则；特殊情况见末尾另行处理。

### 通用原则

- **不加括号补充说明**：标题里不用 `（…）` 做注解。限定信息要么融入正文，要么紧贴通用名称，要么改成语义完整的短语。
  - 反面：`配置 C++ 环境（WSL2）`、`构建系统（CMake）`
  - 正面：`在 WSL2 上配置 C++ 环境`、`用 CMake 构建 C++ 项目`、`标准库 STL`
  - 反面（步骤标题带「可选」与括号）：`第 2 步：升级已装包（可选，保持系统为最新）`
  - 正面：`第 2 步：升级已装包以保持系统最新`
  - 反面（步骤标题塞解释 + 多余族系）：`第 3 步：GNU 编译与调试工具链（编译器 + 调试器，同属 GNU 家族）`
  - 正面：`第 3 步：编译与调试工具链`（新人无需先懂 GNU；解释留给正文/子弹）
- **步骤标签以动词开头，保持节奏一致**：「第 X 步：」后的短语走「动词 + 名词」结构，不要直接甩工具名（名词短语）。
  - 反面：第 5 步：LLVM/Clang 工具集。（名词开头，与「第 1 步：更新…」「第 2 步：升级…」的动词结构断裂）
  - 正面：第 5 步：安装 LLVM/Clang 工具集。（补动词"安装"，节奏一致）
- **标题不随意用 `/` 符号**：多个症状/并列项不要用 `/` 硬拼；性质相近的合并成一条，用概括性标题点出共同本质；确需并列时用中文「与/或」或空格。
  - 反面：`### wsl 安装没反应 / 命令找不到`（`/` 拼症状、未概括本质）
  - 正面：`### WSL2 提示不是内部或外部命令`（症状即标题、工具名大写纯文本，见 常见问题环节）
- **同组风格一致**：同页 / 同层级的标题，统一用「名词短语」或「动宾短语」，不混搭到刺眼；长度克制（卡片 ≤12 字，小节标题尽量 ≤16 字）。
- **术语不翻译、不缩写错位**：RAII、STL、CMake、UB 等专有名词保持英文原样；标题优先用通用中文作主体（「标准库」而非把 STL 当主体），标识符可附后。
- **标题内不用句号**，短促有力；外层可用全角标点（，：；！？「」（））但不堆砌。
- **标题中命令/工具名保持产品级写法**：用大写纯文本（WSL2），不用行内代码小写（`wsl`）；命令的小写行内代码形态只出现在正文（命令槽）。

### 词序与词性（名词 / 动词怎么排）

按内容性质选词性与词序，**同一层级只选一种**，不混搭：

- **概念类（名词短语）**：`〔限定〕+ 核心名词`，核心名词收尾，便于扫读抓主题。例：`移动语义`、`标准库容器`、`现代 C++ 类型推导`、`C++ 环境`。
- **操作 / 步骤类（动宾）**：`〔状语 / 介词短语〕+ 动词 + 宾语`，动词起头表动作，条件 / 位置用介词短语前置。例：`在 WSL2 上配置 C++ 环境`、`用 CMake 构建 C++ 项目`、`配置环境变量`。
- **结果 / 目标式优先**：无论名词还是动宾，标题尽量说清「得到什么 / 能做什么」，如 `迁移 WSL2 系统到其他磁盘` 优于 `导出备份与导入迁移`。
- **并列**：同类用 `、` 或 `/`，不混词性；不用「的」堆砌长定语（`标准库里的容器` → `标准库容器`）。

### 正文标题（章 / 节 / 小节）

- **层级单一信息源**：章用 YAML `title:`，正文不要再写同文本 `# H1`；页面内小节从 `##` 起，子节 `###`，不跳级（结构细则见 `../quarto/basics.md` 与 AGENTS.md）。
- **命名风格**：概念章用名词短语、操作章用动宾，依上节词序；小标题用「目标 / 结果」式，不堆砌操作动作。
- **渐进式披露**：标题下首段写动机 + 目标（1–3 句，正文段落），不预演 `##` 小节内容；命名 callout / 普通 callout 放在引言之后，不顶在标题下。
- **交叉引用**：章节若被 `@sec-` / `#anchor` 引用，改标题文本前先 grep 引用点，避免断链；锚点由标题自动生成，无需手填。

### 卡片标题（首页 landing-card）

卡片是章节入口，文本可与目标章节 `title` 不同，但须语义对应、不强行复制。

- **不加括号**（见通用原则）。限定信息两种处理：
  - 融入标题正文（介词 / 动宾）：`在 WSL2 上配置 C++ 环境`；
  - 紧贴通用名称、不加括号：`标准库 STL`（通用 + 标识符）；若紧贴后读起来拗口（如 `构建系统 CMake`），改用语义完整的动宾短语：`用 CMake 构建 C++ 项目`。
- **默认动宾 / 介词动宾**；纯概念总览可用「通用名词 + 标识符」。与同页其他卡片风格一致。

### 特殊情况（另行处理）

- 标题文本改动导致 `@sec-` / `#anchor` 引用失效 → 同步改引用点。
- 文件名 / 目录名须纯 ASCII（`scripts/check_ascii_names.py`），与标题中文无关，新建文件时另查。
- 需标注引入版本（如 `C++20 引入`）→ 放正文首句，不进标题。
- 需强制强调的短标签（eyebrow / 徽章）→ 用组件（`.hero-eyebrow` 等）承载，不塞进标题括号。
- **book `part:` 名称与面包屑**也适用本规范（去掉「X：」部件标签式，改用名词短语 / 动宾）；改动需同步 `_quarto.yml`、`AGENTS.md` 与首页 `##`，并保持三者一致。

## 去重与主题聚焦

- 引言只写动机 + 目标，不展开细节；细节留给后续小节。
- 同一信息若同时出现在「引言 + callout + 小节」，只留一处。
- 主题聚焦：callout 只放与本章主题直接相关的内容；无关对照（如「关于 MSVC」）不入环境章节。
- 具体化（点名本章环境/工具）：本章若围绕某个具体环境或工具展开（如「搭建 WSL2 环境」章体验的就是 WSL2 Ubuntu），正文、目标列表与描述应直呼其名（WSL2 Ubuntu 环境），不泛化为「Linux 环境」「开发环境」等空泛词，让读者明确本章体验的就是它。
- 近邻不重复：若某信息紧接的下一句会再出现，前句不必提前给出。段落级的同类重复见 相邻段落（内容重复 / 接近时合并）。
- **主旨对齐**：小节段落顺序跟随标题主旨——标题承诺的动作（如启动、关闭）各占一段先行、命令直接入句，支撑信息（查状态、速查表）后置，不反客为主。
- **量词与实际一致**：「几个」「多项」须与实际条目数相符；只有一项时用「一项」或不用量词。

## 命名 callout

关键结论用两个命名 callout 强调，与普通 note/tip/warning/important/caution 区分（写法见 `../quarto/authoring.md`）：

- **最佳实践**（`.callout-best-practice`）：绿色，给出「应该这样做」的规则，如「永远初始化变量」。
- **关键洞察**（`.callout-key-insight`）：金色，点出本章最核心的心智模型，帮助读者「理解知识」而非死记。

一条 callout 只承载一个可复用的结论；简短提醒用 `>` 引用块，不用 callout。

### callout 句式

- **注意对比式**：一条「注意」说清易误解行为，用「X 而不是 Y」对比收束。例：「注意配置文件是合并在一起的，而不是替换。」
- **警告 + 后果句**：先给结论，再给后果。例：「警告实验性选项不稳定。它们可能会在不另行通知的情况下被更改或移除。」
- **提示受众推荐**：例：「如果你是新用户，我们建议从 OpenCode Zen 开始。」
- **破坏性操作告诫**：后果一句（「你对那个文件做的任何修改都会消失」）→「除非确实清楚，否则不要使用」→ 更好做法指针（「……通常是更好的做法」）；同命令多形态时写明哪个安全哪个危险（「不加选项地调用并不危险，它只会修改暂存区域」）。
- **可恢复边界句**：破坏性操作段末给安全边界（「任何已提交的东西几乎总是可以恢复的，然而任何未提交的东西丢失后很可能再也找不到了」）。
- **版本锚定 Note**：章首或行为随版本漂移的主题小节首用 Note 一次声明写作/测试时版本 + 兼容范围（「本章示例在 CMake 3.28 上验证，更早版本的用法可能有差异」），不在每条命令处重复标版本。

## 常见问题（FAQ / 速查）环节

每章末尾用「常见问题」替代测验——**目的是方便新手快速查看问题、理解知识，不是测试**：

- 用问答形式：问题加粗，答案一句到位；每条 1–2 行，扫一眼就能懂。
- 问题来自新手最常踩的坑或最易误解的点；答案直接给结论，需要时再补半句「为什么」。
- 只收「高频、一句话能答」的问题；需要长篇展开的内容放正文小节，不塞进常见问题。
- 安装/配置类「排错场景」用「排错型」写法：`##` 导语只放核心框架句；排错条目**症状即标题**（`###` 直接用报错原文或症状，不加引号），正文 = 现象一句归因 + 「排查步骤」按「前提检查 → 功能/配置 → 装好后仍出现时的处理」排定顺序（这是作者的组织原则，正文用「依次排查」带过，不向读者写「按优先级」字样），每条「**名词标签**：动作 + 归因」；`####` 情形小节仅限同一症状多个互斥成因；详见 `cases/faq.md`「排错型」。
- **排错句式**，按场景取用：
  - **排查闭环**：症状 → 先排除嫌疑项 → 验证 → 定位。例：「如果桌面应用在启动时崩溃、卡住或行为异常，请先禁用插件。」→ 步骤 →「如果应用恢复正常，请逐个重新启用插件，找出导致问题的那个。」
  - **要解决…：**：步骤前引导 + 步骤后结果句。例：「要解决提供商包问题：」+ 步骤 +「这将强制 OpenCode 下载最新版本……通常可以解决模型参数和 API 变更带来的兼容性问题。」
  - **错误码归因**：「如果你遇到 ProviderInitError，很可能是配置无效或已损坏。」
  - **检查引导**：「如果你在配置提供商时遇到问题，请检查以下几点：」+ 动词起头短列表（简单症状用这种轻量清单，不用优先级编号）。
  - **修复判据/回归点**：排查步骤末尾交代怎样算修好（如「看到『安装 WSL2』第 3 步的输出就说明修复成功」），判据用交叉引用承载、不抄输出值。

> 示例见 cases/faq.md

## 延伸内容环节

章末可用「延伸内容」收录按需查阅、非必读、非排错的进阶内容（如系统迁移、技巧），与「常见问题」（排错/速查）互补；两者 `##` 导语都只写核心框架句。

- `##` 导语：核心框架句带过「按需查阅」，不预演 `###` 首条、不冗余（同 FAQ 层级分工）。
- 段落去冗余（来自 相邻段落 / 去重）：标题已表「延伸/按需」，块末不用「是否…不影响」收尾；导语不重复 `###` 已交代。
- 引用块 `>` 克制（来自 命名 callout / 相邻段落）：caveat 只留必要 1 个；注意块归属哪个方法就紧跟该方法的代码块之后，位置承载归属、不再写「方法 X 的」字样；其余提醒并入正文。
- 小技巧类内容（别名、快捷写法）标注「后续不依赖」——「我们不会在之后的章节中引用到或假定你使用过它们」，读者可放心跳过。
- 列表与代码（来自 列表三步 / 代码分工）：命令单独放代码块；并列方法保持顺序可见。
- 回环：块末一句呼应「按需」，但不与导语复述、不带「是否…不影响」语气。

> 示例见 cases/supplementary.md

## 本章回顾环节

章末「本章回顾」用成就列表呼应章首「本章目标」，与「常见问题」「延伸内容」同属章末收尾；外部链接单列「相关资源」。

- **首句点题引导句（最重要）**：引导句直接给结果（「你已经有了一套能编写 C++ 的…环境」），不用无意义标签（如「下面是本章总结：」），也不用「至此」「具体掌握了」等过渡词，直接以结果开场。
- **直接讲重点，不复读目标列表（去重）**：回顾的内容须是增量信息（怎么确认就绪、下一步能做什么）；bullet 与章首目标逐字重合就是重复；本章目标与成果一一对应、没有增量时，回顾不设列表，用 2–3 句重点句收束（结果 + 确认方式 + 下一步）。不夸大、不预列未实际演练的能力（如未实际调试 C++ 程序，就不写「调试」）。
- **第二人称 + 鼓励式（文风基调）**：用「你」、主动、成就式措辞（「已掌握」「已搭好」），不堆虚词。
- **相关资源（链接写法）**：外部链接单列「相关资源」，用描述性内联链接，不裸 URL。

> 示例见 cases/chapter-review.md

## 首页 Hero 描述（导语）写作

`index.qmd` 的 `description:` 渲染为封面标题下的引导段（Hero），是读者看到的第一句。应**面向读者、说清「你能得到什么」**，不要写实现细节（如「基于 Quarto Book 的…」）。

推荐结构：按**本书章节顺序**罗列覆盖范围（只列一次），再用一句「收尾承诺」点明学完**能做什么**（如「写出并构建自己的程序」）；收尾承诺**不得复述已列出的主题/阶段**，只说收益。罗列顺序须与首页下方卡片/章节顺序一致，避免读者对不上内容。

> 示例见 cases/hero.md
- 收尾句用「你 / 我们」视角，动词起头、短句，不堆虚词。
- 本仓库实例见 `index.qmd`（描述 → 准备篇含环境 + CMake → 语言核心含语言要点 + STL）。

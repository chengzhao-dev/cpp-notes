# 教程源码注释决策依据

## 新人阅读缺口

教程源码既会在正文中显示，也会被读者复制、下载或在编辑器中单独打开。没有文件用途注释时，
读者只能从文件名和正文上下文猜测这个文件负责什么。进入多文件工程后，这种缺口会让声明、
实现和程序入口之间的关系更难建立。

注释也不能退化为逐行翻译。`#include`、`main` 和 `return` 的语法含义已经由语句本身表达，
每行都加一句会淹没真正的学习重点，还会让示例修改时出现大量需要同步维护的重复说明。
教程需要的是最低入口信息，而不是把正文抄进代码。

## 最低注释合同

仓库内可独立打开的完整源码和脚本文件至少在首个有效行给出一条原生用途注释。Shell 有 shebang
时，用途注释紧随其后。用途注释回答“这个文件负责什么”，不承担教完整个语言概念的任务。

首个有效行之后按“用途 + 重点”密度补充注释。只有接口契约、实现关系、首次出现的语言重点或
非显然配置值得再写一条短注释。注释应紧贴被说明对象，使用该语言的注释语法，不写行尾长解释。
自动检查只确认用途注释存在，不判断句子质量，也不规定固定注释数量。

## C++ 文件边界

头文件用途注释说明它公开哪些接口。实现文件说明它实现哪项声明。带 `main` 的程序入口说明程序
完成什么任务。这样读者先建立职责边界，再进入具体语句。

函数体内的注释只用于解释不容易从代码看出的行为、决策或边界。`#include`、赋值、函数调用和
`return` 不逐行解释。同一文件用途注释也不需要在入口函数前再复述一次。教学重点可以在正文中
展开，源码只保留读者在编辑器中仍需看到的提示。

## CMake 与 Shell 边界

CMake 首行说明要构建的目标，后续只给标准与输出、编译数据库、源文件收集、包含路径和编译链接
选项等非显然块写职责注释。命令短小且名称已经表达用途时不再补注释，避免构建配置被说明淹没。

### 配置注释的连贯性

配置注释应说明代码会产生什么结果，以及关键选项怎样改变后续行为。`CMAKE_EXPORT_COMPILE_COMMANDS`
的主要结果是生成编译数据库，不应把 clangd 写成唯一目的。源文件收集注释则把“收集范围”和
“新增文件后重新配置”放在同一条因果说明中，读者不需要自己补出两步的关系。

顶层 CMake 和库子目录 CMake 的文件用途注释分别描述自己的职责。顶层说明怎样组合应用与库，
库文件说明构建哪个库目标，两者不互相复述，也不让读者从两个文件拼出一个不完整的职责边界。

### 目标创建注释

`add_executable()` 和 `add_library()` 定义工程中的目标边界。读者阅读 CMake 时，需要先知道当前
命令创建什么目标、它在工程中承担什么职责，才能理解后续包含路径、选项和链接关系属于谁。

目标命令名只表达语法，目标职责来自项目设计，因此创建命令前需要一条独立注释。这一步不同于
`#include`、`main` 和 `return`：后者可由代码本身直接表达，前者建立的是文件和目标之间的关系。

Shell 首行说明脚本用途，并为 `set -euo pipefail` 这类会改变执行语义的设置写短注释。配置、构建
和运行命令保持原样，除非某个选项会影响理解或容易误用，否则不逐条解释。

## 与正文和命令块的分工

inline 命令块仍遵守 `writing-quarto` 的代码块注释规则，以总注释说明整块任务，以子注释补充不明显
的依赖或用途。`include` 引用的真实源码文件脱离文档后仍要可读，因此使用本文件的文件用途合同。

正文负责原因、概念边界、参数差异和验证结果，源码注释负责就地标记角色和观察重点。两者可以
形成接力，但不互相抄写。`writing-cpp/references/cpp/code-style.md` 保存写作侧的操作规则，
本文件只保留这样取舍的依据。

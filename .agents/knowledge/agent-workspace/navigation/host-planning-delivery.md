# 计划生命周期与本地交付默认

计划模式、计划展示和执行进度是宿主客户端的能力，仓库只承载被计划改变的最终文件。本文说明这条边界，以及由它推出的交付默认值。

## 计划生命周期由宿主承载

1. 计划模式约束的是「改动前先给出方案」。模式切换、计划展示和步骤状态都由宿主负责，生成计划文件不是它的承诺。
2. 宿主已把计划渲染成结构化列表并跟踪勾选状态。仓库再落盘一份 Markdown 会出现第二个权威状态，两边的时机与格式不一致时无法判断谁对。
3. 在仓库里定义计划模板、完成标记和校验，等于把规则绑到宿主的协议细节上。宿主升级后这些校验静默失效，维护成本却留在仓库。
4. 所以仓库不设立计划文件、目录和校验：宿主管过程，仓库只在获得明确批准后落盘被改变的最终文件。

## 默认本地交付的依据

1. 本地写入可回滚，推送会改写公共历史并触发部署，两种代价不对称，默认停在可回滚的一侧。
2. 「检查通过」与「已经上传」是两件事：`check`、`verify`、`render` 和 `build` 只证明工作区产物可用，远端状态还需要凭据、网络和时间。
3. 用户没要求远端操作时去做属于扩大范围，可能把未达标的中间状态推上去。
4. 因此默认只交付本地改动；用户明确要求后才提交和推送，范围只覆盖其列出的路径组与目标分支。
5. 一旦要求就要求完整闭环：暂存、提交、推送、远端 SHA 与 CI/Pages 核对缺一不可，没有远端证据就不能写「已推送」。

## temp/ 不是权威状态

1. `temp/` 存放可再生的中间产物，例如知识库索引和一次性分析报告。判断标准是「删掉后能否重跑得到」，不能重跑得到的结论属于文档或知识库。
2. 中间产物可跨轮次复用，但不能当完成证据：结论必须来自当前工作区的实际检查输出。
3. 宿主维护的计划与进度同样不算完成证据，只有磁盘上的最终文件与检查结果才算。

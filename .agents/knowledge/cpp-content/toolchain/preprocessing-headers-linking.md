# 从源码到可执行程序的阶段边界

## 源码到可执行程序的阶段链

一个多文件 C++ 程序不是由 `#include` 一步变成可执行文件，而是依次经过预处理、编译、链接、加载和运行。教学内容应把这些阶段作为不同的验收点：

```text
源文件
  → 预处理：形成翻译单元
  → 编译：每个翻译单元生成目标文件
  → 链接：解析符号并组合目标文件
  → 可执行文件
  → 加载与运行
```

### 预处理：形成翻译单元

预处理器处理 `#include`、宏和条件编译，形成交给编译器的翻译单元。`#include "greeting.h"` 的作用是让当前源文件看到头文件中的声明；它不会把 `greeting.cpp` 的函数定义链接到程序中，也不负责寻找库的二进制实现。

### include 与翻译单元

尖括号和引号表达不同的头文件查找意图。`#include <string>` 通常用于标准库或外部库，`#include "greeting.h"` 通常用于项目头文件。实际搜索目录由编译器实现和 `-I` 等参数共同决定，不能把写法解释为固定的完整路径规则。

### 编译：分别生成目标文件

每个 `.cpp` 文件都独立编译为目标文件，例如 `main.cpp` 生成 `main.o`，`greeting.cpp` 生成 `greeting.o`。目标文件包含机器码、符号和重定位信息，但通常还缺少跨文件调用所需的最终地址，因此不是可以直接运行的完整程序。

声明让调用点通过类型检查，定义提供函数体和可链接的实现。调用点缺少声明时，错误通常发生在编译阶段；声明存在但构建命令没有提供定义时，编译可能成功，错误会推迟到链接阶段。

### 链接：解析符号并生成可执行文件

链接器接收目标文件、静态库和必要的系统库，解析跨文件符号，完成重定位并生成可执行文件。若 `main.cpp` 调用了 `makeGreeting()`，链接输入必须包含提供该函数定义的 `greeting.o` 或对应库；否则常见诊断会包含 `undefined reference`。

静态库中的目标代码在链接时被选入最终程序，因此分发程序时通常不需要再把该静态库作为运行期文件放在旁边。动态库通常不被复制进可执行文件本身；程序启动时由运行时加载器查找并加载 `.so`，所以“链接成功”和“程序能启动”是两个不同的验收点。

### 加载与运行：验证最终产物

运行命令把可执行文件交给操作系统。操作系统加载程序及其运行期依赖，程序从 `main()` 开始执行并写入标准输出。动态库缺失、搜索路径不正确或权限不满足，都可能在链接成功后才暴露。

因此，最小验证应至少分成两步：先确认链接生成了可执行文件，再启动该文件并检查输出。不能用“某个 `.cpp` 能编译”替代完整目标的链接和运行验证。

## 声明、定义与头文件保护

### 声明、定义与链接输入

函数声明告诉编译器名称、返回类型和参数类型；函数定义提供函数体。多文件程序通常把跨文件共享的接口声明放在头文件，把实现放在源文件，再把所有实现文件交给同一个可执行目标或库目标。

### pragma once 的标准边界

`#pragma once` 是广泛支持的实现扩展，不属于 ISO C++ 标准。传统宏 include guard 提供更严格的标准可移植写法。两者都只防止同一头文件的声明文本重复进入翻译单元，不能替代正确的定义、目标文件或链接配置。

## 相关边界

- 找不到头文件：通常是预处理或编译阶段的包含路径问题。
- 找不到函数定义：通常是链接输入缺少目标文件或库。
- 动态库找不到：通常是程序启动时的运行期搜索路径问题。

# 中文技术文档润色九项原则

本文件是技术写作与审校的最高优先级规则。更新文档或合并请求前先按本文件自查。规则冲突时，以受众导向和可验证性为最终裁决标准。

## 核心原则概览

| 序号 | 原则 | 解决的核心问题 | 适用场景 |
| :---: | :--- | :--- | :--- |
| **1** | **受众导向** | 自说自话、知识诅咒、信息错位 | 所有文档的开篇与背景介绍 |
| **2** | **结构先行** | 逻辑跳跃、重点淹没、阅读疲劳 | 长文档、架构设计、操作指南 |
| **3** | **术语一致** | 概念混淆、翻译腔重、认知负荷高 | 跨文档协作、API 参考、术语表 |
| **4** | **动词驱动** | 被动冗余、指令模糊、行动力弱 | 操作步骤、CLI 指南、故障排除 |
| **5** | **格式降噪** | 视觉混乱、层级不清、关键信息遗漏 | 排版、代码块、Callout 使用 |
| **6** | **可验证性** | 步骤缺失、环境依赖不明、无法复现 | 教程、Quickstart、部署指南 |
| **7** | **渐进披露** | 信息过载、新手劝退、细节淹没主线 | 入门指南、复杂系统架构、书籍式文档 |
| **8** | **权衡透明** | 盲目跟风、缺乏理据、技术债累积 | 规范制定、架构决策、最佳实践 |
| **9** | **语感自然** | 翻译腔重、从句冗长、现代中文失范 | 全文润色、对外发布、技术博客 |

## 1. 受众导向

**不为展示知识而写，只为解决读者问题而写。**

- 开篇明确谁在读、读什么、读完能做什么，不堆砌无关背景。
- 区分新手引导与专家参考，不在同一文档中混合不同深度的内容。
- 预判读者的痛点与误区，主动解释为什么，而非只陈述是什么。
- 避免内部黑话或未定义的缩写，除非目标读者确知该术语。
- 按摘要、细节、补充链接的顺序提供信息。

检查标准：非作者本人能在 30 秒内判断文档是否匹配当前任务，并找到所需答案。

## 2. 结构先行

**用金字塔结构组织信息，让读者按需取用，而非线性忍受。**

- 先给结论、命令或核心方案，再展开理由与细节。
- 长文档提供目录或导航锚点，章节标题应承载信息，不只充当标签。
- 将复杂流程拆成独立子任务。每个任务说明输入、操作和输出。
- 优先用列表表达并列关系、用表格对比多项属性、用代码块呈现可复制的多行示例。
- 删除“众所周知”“显而易见”等没有信息量的过渡语。

检查标准：随机抽取任意段落，若脱离上下文无法理解它要解决什么问题，应重构结构。

## 3. 术语一致

**建立并严格执行术语表，消除歧义是专业性的底线。**

- 同一概念在全文和跨文档间只使用唯一译名或原文标识。
- 优先采用行业标准术语，避免生造词汇。
- 英文专有名词保持原有大小写，不作没有检索价值的汉化。
- 首次出现时给出全称与缩写对照，后续统一使用一种称呼。
- 区分易混词，并在术语表中说明其边界。

检查标准：全局搜索任一术语，结果应指向同一实体，替换任一译名不应改变语义。

## 4. 动词驱动

**用主动语态和强动词构建清晰指令，消灭官僚体与翻译腔。**

- 操作类文档使用祈使句，例如“执行”“检查”“创建”，避免“应该被”或“建议用户”。
- 将名词化表达还原为动词，例如把“进行数据的分析”改为“分析数据”。
- 避免双重否定与长定语从句。超过 40 字且包含多个动作的句子应拆分。
- 描述系统行为时明确主语，例如“API 返回错误”，而非“错误被返回”。
- 用“超时”“阻塞”“降级”等精确动词描述状态，替代笼统的“异常”或“问题”。

检查标准：朗读时需要换气两次才能读完，或听起来像机器翻译的句子，应立即重写。

## 5. 格式降噪

**排版服务于可读性，形式永远服从于功能。**

- 路径、变量、命令行参数和其他需要精确识别的短技术对象使用行内代码。
- 可复制执行的多行命令与完整示例放指定语言的代码块。命令与输出分块，输出放紧随其后的 `text` 块。
- 警告、注意和提示使用项目规定的提示样式，不滥用颜色或加粗。
- 中英文之间保留空格。链接标签内不套行内代码。
- 列表项保持语法平行，相邻项的信息密度接近。
- 图片必须有 Alt 文本和说明。图表必须给出坐标轴标签和单位。

元素选型、Callout 语义和链接间距细则见 `references/quarto/authoring.md`，命令与输出细则见 `references/quarto/terminal-validation.md`。本文件不维护第二套格式规范。

检查标准：去除样式后的纯文本仍可读，恢复样式后，视觉重心自然落在关键操作上。

## 6. 可验证性

**文档不是文学作品，每一段都应能被执行、测试或证伪。**

- 操作步骤给出预期结果或验证命令，禁止以“然后就好了”收尾。
- 明确前置条件、环境版本、权限要求和已知限制。
- 示例代码必须完整可运行。省略部分必须用注释明确标注。
- 变更日志记录具体影响范围与回滚方案，而非只列版本号。
- 定期执行文档中的操作，修复产品迭代造成的失效内容。

检查标准：新人无需口头指导，能仅凭文档完成端到端操作并确认成功。

## 7. 渐进披露

**控制认知负荷，先建立心智模型，再深入底层细节。**

- 分层提供 Quickstart、核心概念和深入原理，使读者按需停留或继续。
- 基础用法不提前引入边缘 Case 或高级配置，避免干扰首次成功路径。
- 明确列出前置知识，并给出补课入口。
- 先展示接口或高层行为，再解释底层实现机制。

检查标准：初学者跳过深入原理仍能完成基本任务，资深读者能通过深入原理解决疑难问题，且两条路径互不干扰。

## 8. 权衡透明

**没有银弹，说明为什么这样做比只说明怎么做更重要。**

- 除了最佳实践，也给出反模式及其错误示例。
- 规范限制了看似流行或直觉的做法时，解释性能、安全性和维护成本等工程理据。
- 明确方案的适用场景、失效场景和代价，不夸大收益。
- 需要作决策时，列出被否决的替代方案及其原因。

检查标准：读者遇到规范限制时，能从文档理解其理由，而不是只看到结论。

## 9. 语感自然

**遵循现代中文的意合特征，消除翻译腔，追求流畅的技术表达。**

- 避免连续三个以上“的”。例如将“用户的配置的文件的权限”改为“用户配置文件权限”。
- 将“当……的时候”简化为“……时”，将“基于……的原因”简化为“因为……”。
- 按逻辑顺序自然衔接句子。例如“启动服务，检查日志”优于冗长的时序从句。
- 慎用“关于”“对于”“作为”等介词开头的长句，直接以主语或动词破题。
- 正文用短句。一句话只说一个动作或一个结论，主语能省就省。
- 长难句只在确实更清楚时使用。拆开反而要重复主语、读者需要来回拼接时，保留长句。
- 正文不用分号。并列分句改用逗号，语义独立的分句改写成两个句子。

句长、分号、措辞替换和中文表达案例见知识库 `cpp-quarto-chinese-style-v1`。本文件只保留审校原则和结论。

检查标准：非技术背景的中文母语者读起来像在读外语或觉得拗口时，应重写。

## 段落与块级内容四步审校

1. 判断职责：先确认这段内容是在承诺结果、执行动作、说明验收、补充背景还是连接下一步。
2. 决定合并或拆分：同一对象和同一结论保留在同一段，不同职责或会打乱执行顺序的内容拆开。
3. 做删除测试：删去后不影响当前成功和验收的细节移出主线，必要时放到任务末尾的 Callout。
4. 收束边界：统一代码块前的标点、中英文空格、行内代码和链接边界，再检查正文与 Callout 是否重复。

小节与 Callout 的具体分工见 `references/zh/section-focus-and-density.md`，代码块前标点与命令输出写法见 `references/quarto/terminal-validation.md`。

## 附录：文档审校 Checklist

### 基础检查

- [ ] 开篇是否明确目标受众和前置知识？
- [ ] 所有专业术语是否与全局术语表保持一致？
- [ ] 操作步骤是否使用动词开头的祈使句？
- [ ] 代码块是否指定正确的语言高亮？命令与输出是否分块并给出验证方式？
- [ ] 中英文混排时，是否遵守了加空格规范？
- [ ] 链接标签两侧间距是否符合“英文留、中文不留”，标签内是否残留行内代码？
- [ ] 读者是否能仅凭此文档完成操作，无需额外询问作者？

### 进阶检查

- [ ] 是否提供不同深度的阅读路径？
- [ ] 对限制性规范，是否说明了理据、收益和代价？
- [ ] 是否存在连续三个“的”或超过 40 字且含多个动作的长句？
- [ ] 正文是否使用了分号，能否改成逗号或拆成两个句子？
- [ ] 每个句子是否只推进一个动作或结论，新人能否一遍读通？

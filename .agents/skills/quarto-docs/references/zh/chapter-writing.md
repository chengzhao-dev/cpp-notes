# C++ 学习轨迹笔记章节写作

先遵循 `writing-principles.md`。本文件只规定本项目的页面组织和 C++ 教学写法，Quarto 元素细节见 `references/quarto/authoring.md` 与 `references/quarto/terminal-validation.md`。

## 读者与范围

读者有编程基础，但可能第一次接触 Linux、C++ 工具链和工程构建。每页只解决一个读者任务，保留标准术语，并在首次出现时用一句话解释。正文少讲背景，先让读者完成一个可验证动作。

项目使用“笔记、内容、部分、页面、阅读顺序”等中性词，不写成课程或教材。运行环境以 Linux 为准，Windows 读者通过 WSL2 获得同样环境。正文优先使用 C++20。

## 页面骨架

正文按“引言 → 任务步骤 → 常见错误 → 简短回顾”组织。只有静态对象或路线必须先说明时，才加独立概览。引言说明读者为什么开始、能完成什么，不复述标题、命令或结果。

- 每个 `##` 承担一个阶段，`###` 只用于有独立动作或结果的子任务。标题写任务或可观察症状，不手填序号。
- 有效顺序是“做什么 → 执行什么 → 看到什么 → 简要说明”。不要一次塞入多个成功路径。
- 先给可运行结果，再解释目录树、参数和实现细节。可选分支放在主线完成后。
- 正文只写正确路径，故障放进“常见错误”。一个故障按“定位 → 修复 → 验证”展开。
- 并列的三步诊断中，某一步需要执行可复制命令时，使用与相邻步骤一致的“说明句 → 代码块”结构。只有该步骤确实不含命令时，才只保留说明文字。
- 三项以上且需要比较属性时才用表格。对照表放在主线跑通之后。
- 回顾只用一段总结和最多三个本章问题，不要重复全书路线。

## 命令与示例

- 代码块前说明目的，代码块后给输出或验证方式。命令与输出分开。
- 目录树、命令和输出必须来自实际工程。只展示当前任务需要的文件。
- 完整源码放在 `code/` 中，正文通过 `{{< include >}}` 引入。
- 示例必须能编译、运行，正文承诺的输出必须与实测一致。不要用未验证的长输出证明程序正确。
- 首次出现的术语给出中文名称、必要英文检索词和一句白话解释，后续固定称呼。
- 新术语必须由当前任务中已经出现的对象、状态或动作引出，紧接着解释它和当前步骤的关系，再进入命令或下一步。与当前动作无关的背景事实不插在命令前后。
- 删除低价值输出解释。只有读者需要据此判断结果时，才解释产物类型或内部格式。

## 页面类型

### 环境页

从上一页的可观察状态开始，只安装继续操作所需的工具。安装过程保持一个成功路径，命令后说明下一步何时需要重新执行。

### 构建页

先展示最小源码和构建规则，再依次配置、构建、运行。目录树、源码和命令要指向同一个目标名和产物路径。直接编译与 CMake 构建分开讲，避免把两种工具塞进一条流程。

首次程序要说明 Hello World 为什么适合验证最小链路。展示 `main` 后，明确指出 `main()` 后面的花括号组成函数体，程序从函数体中的第一条语句开始执行，不只写“执行花括号中的内容”。

### 工程页

先说明多文件工程解决什么问题，再展示接口、实现、入口和构建规则。正文解释每个文件承担什么职责，不提前展开所有 CMake 选项。

### 库页

静态库和动态库各占一页。静态库说明库代码如何进入程序，动态库说明程序运行时如何找到库文件。两页都用同一组源码，只在链接和运行时行为上比较。

## 收尾

页面最后给出下一页能继续使用的状态。需要检索领域原因时，用 `run.py kb-search` 加 `--domain quarto-docs`，不在本文件复制知识库案例。

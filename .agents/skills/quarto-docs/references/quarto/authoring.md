# 文档内容写作

## 文件关系先于单页润色

多个页面一起修改时，先确定入口、索引和正文的职责。入口只回答“这是什么、从哪里开始”；索引只安排顺序；正文负责一个可完成的任务。前置页面不要提前展开后续章节的命令，正文也不要重复索引已经给出的路线。

包含实际源码和构建结构的章节，应在第一次展示源码前加入目录树。先用命令查看真实目录和文件名，再按 `project-tree-and-diagram-focus.md` 筛选读者需要认识的内容；目录树可排除 `.cache/`、日志、对象文件和 CMake 内部缓存，但参与维护的同类配置不得只展示一部分。入门工程按 `.vscode/`、`build/`、`.clangd`、`.clang-format`、`.clang-tidy`、脚本、`CMakeLists.txt`、源码的稳定顺序展示，树内用对齐的行尾 `#` 注释职责。正文只在树前用一句任务导向的话引出目录，不提“实际目录”或“教学视图”，树后不逐项重复注释内容。

> 写或改 `.qmd` 正文、标题、代码块和终端命令时阅读本文件；本文件同时覆盖图表、表格、Callout、FAQ 与交叉引用。

## 章节标题与开篇

- 章节标题由 YAML `title:` 提供，不再写同文本的 `# H1`；页面小节从 `##` 开始。
- `##` 与 `###` 不手动加 `一、`、`1.1` 之类的序号。本书 `_quarto.yml` 设了 `number-sections: false`，序号只能靠手填，一旦增删或调换小节就与目录、上下文和「见 X.Y」式引用对不上，标题锚点也会带上序号。标题只写读者要完成的任务。
- 较长的 `##` 按“概念 → 操作 → 验证 → 问题排查”拆分为必要的 `###`；短内容不为凑层级增加标题。
- `###` 只用于独立任务、示例、验证或排查流程。只有一两句话的内容并入相邻小节。
- `##` 下只有介绍性列表、短句或两三项并列内容时，不单独创建 `###`；索引页的 `##` 仅承担分组作用。
- 每个小节开头先说明目标，再给解释、操作和判断标准。句子按“目标 → 原因或条件 → 动作 → 结果”推进，使用“因此”“不过”“完成后”等词时，确保前后句确实存在因果、转折或时序关系。
- 标题与首段一体：首句兑现标题承诺（结论或动作），不要用背景信息推迟回答。
- 章节导语按“上一章结果 → 本章动作路径 → 最终验收”自然衔接；优先使用“先……再……最后……”等连接，避免连续使用“即说明”“负责”“本章完成”等制度化表达。验收结论只在最需要的位置出现一次。
- 首页和卡片先说主题与学习结果；不要把 API、命令或完整小节提纲塞进卡片描述。
- 新手必须掌握的内容放正文；规则、风险和易忘内容使用内置 callout。章末保留简短回顾、下一步和必要 FAQ。

## 长章节的骨架

`##` 表示一个可以独立完成的学习任务；当一个任务同时包含概念、多个操作阶段和验证时，才使用 `###` 拆分。推荐按“为什么需要 → 最小示例 → 实际操作 → 验证 → 排查”递进。内容很多时增加有意义的 `##`，不要用空泛标题或大量短小小节填充篇幅。每个小节开头先说明目标，结尾说明结果和下一步。

开发环境说明按“Windows → WSL2 上的 Ubuntu → 编辑器 → 构建工具”展开，保持 Windows、Ubuntu、VS Code 和 CMake 的职责清晰。直接使用具体名称，不使用抽象的环境称呼。

全文应从目标和前置条件开始，经过问题场景、心智模型、最小示例和操作，最后进入验证、排错、练习或迁移与回顾。不要为了“完整”把不影响首次成功运行的工具和命令提前塞进环境章节。

当一次任务涉及 README、索引页和多个章节时，先按章节路线分配内容，再统一标题、术语、命令和链接。前置文件负责入口与范围，章节负责具体任务；不要让每个文件重复介绍同一环境。README 和首页面向读者，只保留入口、最短路径和必要命令；维护规则与详细规划放到对应的 skills、AGENTS 或运维文档。章节应让读者看到可运行结果，再说明完成当前任务所需的规则。

正文只写当前章节能够完成的事情。不要用“解释为什么……”作为标题或目标，除非后文确实提供了对应的完整说明；仅展示操作时，使用“查看、编译、运行、验证”等中性表达。插件配置和随版本变化的编辑器界面不进入入门流程，必要信息通过官方文档链接提供。

## 重构与事实核对

重构默认在原文基础上进行：先读取原文件、相关引用和任务边界，再局部调整结构、表达和衔接。只有用户明确要求，或原结构无法安全修复时，才删除后重新生成。目录、文件名、版本号、命令输出和工程结构等可从磁盘或命令获得的内容，必须先实际获取；无法确认时只写检查方法，不伪造结果。

需要改名、提取或拆分时，先比较新旧文件的职责和关联，再决定保留哪些内容。拆分后同时复核所有相关文件，统一术语、顺序、链接和重复内容；有效信息不得因文件调整而无依据丢失。

## 代码块

使用普通语言围栏 `cpp`、`bash`、`powershell` 或 `cmake`，不写 `{.cpp}` / `{cpp}`。若复杂关系确实需要 Mermaid，必须使用 ```` ```{mermaid} ````，不能写成普通的 ```` ```mermaid ```` 代码块；正式 C++ 教学主线遵循工程目录树 reference 的限制。代码块上方用一句正文说明用途；真实仓库示例优先用 `{{< include /code/.../file >}}` 引用。

`{{< include >}}` 引用真实代码文件时必须整体包在带语言名的围栏里，没有例外：`.cpp`/`.h` 用 `cpp`、`.sh` 用 `bash`、`CMakeLists.txt` 用 `cmake`、PowerShell 脚本用 `powershell`。裸写的文件内容会被当成 Markdown 解析，`#` 注释行变成标题、`*` 和 `_` 变成强调，页面呈现乱码式排版，以 `#` 开头的行还会混进右侧目录。

代码高亮统一使用 GitHub Light / GitHub Dark，唯一配置来源是 `_quarto.yml`。语义颜色交给 Pandoc/Quarto；命令与输出分块展示，细则见 `terminal-validation.md`。

代码块中的注释只解释本节重点。重要代码行在对应行正上方使用该语言原生注释；不支持注释的格式不强行插入。复杂原理放在代码块外，避免逐行翻译。注释不引入正文尚未出现的比较对象，也不把未使用的备选配置写进示例。Shell 整份脚本的用途注释放在 shebang 与 `set -euo pipefail` 之间，说明的是文件本身；展示脚本时保留 `set -euo pipefail`，不要删掉。

图或代码块需要一句附属说明时，用 `:::: {.code-caption}` 紧贴对象（上或下均可）呈现，只写一句话，样式交给主题的次要文字色，不与相邻正文段重复；没有说明就不加。

代码、命令和终端输出统一左对齐并保留源码中的缩进。需要字段对齐时使用表格，不在代码块中用空格拼出表格。正文中的冒号只做简短引出，能用完整句子说明时不要连续堆叠冒号；短命令如 `wsl` 和 `wsl ~` 直接放入正文，不单独占用代码块。命令已经表达清楚时，直接给出命令，例如写“运行 `wsl ~`”，不再改写成“运行带有 `~` 参数的 `wsl ~`”。

## 终端命令约定

命令、说明与输出的展示以 `references/quarto/terminal-validation.md` 为唯一细则：命令进 `bash`/`powershell` 围栏，不加提示符与块内注释；说明写在紧邻的正文段落；输出进随后的 `text` 块。本文件不再重复命令示例。

## 配置文件与 CMake

`CMakeLists.txt`、YAML 和 Dockerfile 等声明式文件，在代码块内部使用其原生注释，注释放在对应语句正上方。CMake 注释优先采用 [CMake 官方中文文档](https://cmake.com.cn/cmake/help/latest)的术语，不复制大段文档。

## 文档类型边界

这套规则的“目标、解释、验证、少重复”原则也适用于 Skill 和 `knowledge/`，但它们优先保持短小、可检索和可执行。Skill 与说明文档默认使用段落、表格、编号步骤和代码块，不为凑结构加入图片或 Mermaid；只有复杂分支确实难以用文字表达时才例外，并补充文字结论。README 遵循 GitHub Markdown，可以保留 Actions、许可证徽章和有信息价值的图片；根目录 `README.md` 是在线阅读链接的唯一入口，根目录 `index.qmd` 不重复放置该链接；`AGENTS.md` 只保留硬性执行规则。

## 行内代码与链接

- 反引号只包裹需要精确识别的技术对象：命令、工具、编译器、调试器、构建系统、参数、文件名、路径、配置键、API、标识符和包名。示例：`g++`、`clangd`、`gdb`、`CMake`、`Ninja`、`cmake --build`、`CMakeLists.txt`。
- 同一对象在同一章节内必须保持一致；不能只标记 `g++`、`clangd` 而漏标记 `gdb`、`CMake` 或 `Ninja`。
- 普通概念、平台和产品名称不自动加反引号，例如 Ubuntu、Windows、VS Code；只有作为命令、路径或精确标识时才标记。
- 指向仓库文件时写成可跳转链接（GitHub blob 或 `page.qmd#锚点`），不用反引号包住路径冒充链接。
- 中英文之间保留空格；行内代码与中文之间同样留空格。

写完章节后，用 `run.py check` 的行内代码检查确认关键工具和命令没有漏标记；该检查只扫描正文，不扫描代码块和完整行内代码。


## 卡片与页面角色

- 卡片只承载主题、范围与学习结果，不堆叠 API、命令和长句。
- 入口页（`index.qmd`）只回答「这是什么、从哪里开始」；part 封面负责顺序与分组；正文负责一个可完成的任务。
- 前置页面不提前展开后续章节的命令，正文不重复索引给出的路线。

## 文档元素
使用项目支持的标题、列表、表格、代码块、图片、交叉引用和提示样式。元素选择服务于结构与可读性，不以装饰为目的。

### 代码与媒体

- 可复制的完整示例使用带语言标记的代码块。
- 图片提供 Alt 文本和说明；图表标注坐标轴与单位。
- 仓库文件使用可跳转链接；短技术标识使用行内代码。

### 提示与引用

提示内容放在所属小节末尾，避免同一事实在正文和提示中重复。交叉引用使用真实标题生成的锚点，引用前确认目标页面存在。

需要本仓库的渲染与输出依据时，检索 `cpp-tooling-quarto-render-v2` 或 `cpp-tooling-quarto-html-v2`。

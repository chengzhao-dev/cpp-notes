# 终端命令与实测输出

本文件是命令、说明与输出展示细则的唯一出处，其他文件只保留指针，不重复展开。

## 命令与结果的顺序

命令块前分别说明执行环境和前置条件，不把权限、系统版本、命令和结果挤在同一句中。推荐使用以下顺序：

1. 说明先决条件和执行位置。
2. 给出可复制的命令。
3. 展示预期结果或真实输出。
4. 说明成功判据和下一步。

有明确先后关系的动作使用有序列表，并列的系统要求、工具要求和注意事项使用无序列表。每个代码块前用一句正文说明目的，块后只写继续操作所需的判据或下一步，安装命令不追加通用成功句。

后续命令依赖前一条命令的输出时，正文必须说明从输出中复制什么、如何用它完成占位符替换，以及什么时候执行下一条命令。例如选择 WSL 发行版时，要从 `wsl --list --online` 的输出中复制目标发行版名称，原样替换安装命令里的 `<发行版名称>`，再执行 `wsl --install -d`。不能只写“记下名称后再安装”，否则新手需要自行判断取值对象和替换位置。

安装后重启、重新登录或重开终端等会切换执行环境时，先说明触发时机和状态变化的原因，再给恢复后的可观察状态或下一步。不要在 Windows 与 Ubuntu、安装动作与重启动作之间留下缺少上下文的直接拼接。

恢复后的可观察状态本身需要拆解说明，并且其后没有必经动作时，可以用结果型 Callout 承接精确判据和说明列表；正文仍要先保留检查动作。结果型 Callout 的边界见 `references/quarto/authoring.md`。

## 代码块前的标点

代码块前不固定使用冒号，按引导句与块内容的关系选择：

| 引导句职责 | 末尾 | 示例 |
|---|---|---|
| 完整动作或条件，命令是下一步执行 | `。` | 以管理员身份执行下面的命令安装 WSL2。 |
| 用“如下、以下、例如”直接引出代码或输出 | `：` | 程序输出如下： |
| 普通过渡，块只是接下来展示的内容 | `。` | 接下来查看工程目录。 |

只有引导句明确把代码或输出作为“如下”等词语的内容时才使用全角冒号。正文不以逗号、半角 `:` 或 `：。` 结束，行内代码和代码块内部照抄真实语法。

## 实测输出

目录、文件名、版本号、工具状态和终端输出应先通过磁盘或命令获取，再写入文档。标记为在 Ubuntu 或 WSL 中运行的只读验证命令，先实际执行，再保留能判断成功的关键行。输出过长时可以筛选版本行、状态行或关键错误，但不能凭空编写结果。

安装、升级和转换发行版等会改变系统状态的命令只展示操作步骤，不在写作过程中重复执行。安装完成后的版本检查可以单独实测并展示结果。环境不可用时只写检查方法，并明确没有实测输出。

不预先编写长段环境校验。逐项运行 `clang++ --version`、`cmake --version`、`wsl --status` 之类命令只能证明「此刻命令可调用」，读者已经安装的软件包不会因此变可靠，一旦环境缺失还得重读一遍诊断流程，收益低于成本。安装命令之后直接进入下一步实际操作，报错时由 FAQ 承接诊断。需要展示版本时，把版本信息作为一次实测输出的副产品，例如配置阶段打印的编译器版本。


## 命令、说明与输出三分法

命令块只放能直接复制执行的命令，以及紧贴在命令上方的原生注释。不加 `$ ` 或 `PS>` 提示符，不在命令行末尾追加注释。每个代码块在首条命令上方写一条总注释，说明整块要做什么；只有单个依赖或用途不明显、容易误用时，才在该命令上方补一行子注释。输出放在紧随其后的 `text` 块中，命令块与输出块之间只留一个空行。没有结果演示时不添加 `text` 块，多条命令之间同样留一个空行。

代码块注释一行只承担一个职责。总注释和子注释都用短句，不用中文冒号或分号串联多个动作。条件、风险和恢复动作写在代码块前后的正文中，需要两个动作时拆成两条注释与命令或拆成两个代码块。代码块中不使用 Markdown 强调符号。

标点规则只作用于正文、标题、表格和列表，行内代码与代码块内部照抄真实语法，不做改写。带命令前缀的列表项例外：`- 运行 `wsl --install`；` 之后被反引号闭合的部分属于正文，仍然受规则约束。把多条命令串进一句话，读者无法判断该复制哪一行，应当拆成独立的代码块或独立句子。

按执行环境选择代码块语言和标题：

| 内容 | 属性围栏 | 约定 |
|---|---|---|
| Linux、WSL 和 Bash 脚本 | `{.bash filename="Ubuntu Bash"}` | 脚本文件用真实文件名；`#` 注释单独成行，写在被说明命令的正上方 |
| Windows PowerShell | `{.powershell filename="PowerShell"}` | 首次安装需要管理员权限时写 `PowerShell（管理员）`；`#` 注释单独成行 |
| 真实输出、目录树 | `{.text filename="输出"}` | 目录树标题写 `工程目录`；不放命令、`$ ` 或 `PS>`，不启用语言高亮 |

提示符会让读者分不清哪一行能复制：一个 30 行的块里真正要敲的往往只有三行，粘贴带提示符的行到终端还会直接报错。注释单独成行不会产生这个问题，它复制进终端会被 shell 忽略，还能让读者脱离上下文看懂每一行的职责。

```{.bash filename="Ubuntu Bash"}
# 安装 Clang/LLVM 编译器、构建工具、调试器和静态检查工具
sudo apt install -y clang clangd llvm lldb libc++-dev libc++abi-dev cmake ninja-build clang-tidy clang-format
```

命令有输出需要展示时，说明成功判据的正文写在两个块之间，输出进独立的 `text` 块。只有后续步骤依赖该观察时才保留成功判据；命令正常结束本身就是隐含结果时，不追加通用成功句。

```{.bash filename="Ubuntu Bash"}
# 查看已安装的 CMake 版本
cmake --version
```

```{.text filename="输出"}
cmake version 4.2.3
```

## 成功判据三件套

输出不稳定或篇幅过长的命令，不展示完整输出，改给可核对的判据。三条按可得性写，不必凑齐：

| 判据 | 写法 | 适用 |
|---|---|---|
| 退出码 | “退出码为 0” | 任何被脚本或后续步骤依赖的命令 |
| 关键行 | “输出包含 `Build files have been written to`” | 交互式执行，读者用眼睛确认 |
| 产物文件 | “`build/bin/app` 存在” | 构建、生成配置、导出数据库 |

配置与构建这类分阶段的命令，两条阶段各自给一条判据，再补一句“两阶段都成功才算流程完成”。判据写在命令块之后，不重复正文已说明的用途。

## 破坏性命令四要素

删除、清空、覆盖类命令进入正文时，必须同时交代四件事，缺一项就不要给出该命令：

1. 删什么：具体路径与其内容性质。
2. 不删什么：读者真正担心丢失的东西，例如源码与构建配置。
3. 如何恢复：能否重新生成，或恢复需要哪些前置。
4. 替代方案：先给出可逆写法（改目录、改名、移动到备份），把不可逆写法放在确认新状态正常之后。

优先展示可逆替代。`rm -rf` 只有在没有安全替代、且恢复路径明确时才写，并放在 warning callout 或独立段落里，不与成功路径混排。

## 常见错误使用三步诊断流

常见错误放在本章回顾之前，`## 常见错误` 负责导航，不能用一个总列表代替故障结构。每个故障用一个描述现象的 `###`，标题后的第一句同时说明触发条件与可观察现象，下面只保留“定位 → 修复 → 验证”三个有序步骤。三步对应读者必须完成的先后动作，不再额外创建 H4，也不使用自定义 `.troubleshooting` 容器或排错表。

定位步骤只放收敛问题所需的最小检查，命令需要复制时使用独立代码块。修复步骤必须复用定位得到的具体对象，并提供回到成功路径的动作。验证步骤给出一个可观察结果，必要时再次执行命令。一个步骤中存在多个可选原因时，在该步骤下使用无序列表；只有顺序会改变结果时才使用有序列表。

修复动作必须与定位得到的故障对象一致。清理目标产物不能替代清除 CMake 配置缓存，排查缓存或工具链问题时也不顺带更换构建类型；诊断优先使用新的 Debug 构建目录，确认替代路径可用后再处理旧目录。

故障标题后的首句直接回答发生了什么或先检查什么，并用一句正文交代恢复顺序。步骤名优先使用“定位、安装、配置、验证”等短动词短语，写成加粗的 `1. **定位失败来源**`，说明文字另起缩进段；只加粗步骤名，说明、命令和参数保持常规字重。验证完成后若仍有主线任务，在可观察结果之后给出明确回流入口。Quarto FAQ 的直答和短段落可供借鉴，但本站处理的是按顺序执行的失败路径，因此保留 `常见错误` 入口，不改成列举式问答页。

````markdown
### 软件源更新失败

执行 `sudo apt update` 时出现下载失败或软件源不可用等错误。按下面的顺序定位失败来源，配置可用镜像源，再重新验证。

1. **定位失败来源**

   确认命令在 Ubuntu 终端中执行，并记录错误输出中的软件源地址和 Ubuntu 版本。

2. **配置可用软件源**

   按[清华大学 Ubuntu 镜像使用帮助](https://mirrors.tuna.tsinghua.edu.cn/help/ubuntu/)为当前 Ubuntu 版本配置软件源。

3. **验证更新结果**

   ```{.bash filename="Ubuntu Bash"}
   sudo apt update
   ```

   命令正常结束且不再出现软件源错误，说明软件源已经恢复，可以回到[安装 C++ 工具链](#安装-c-工具链)继续操作。
````

定位命令需要读者先抄取输出、再把结果用于下一步时，必须单独放在可复制代码块中，并用紧贴命令的原生注释说明用途。例如选择 WSL 发行版时，先用 `wsl --list --online` 查看名称，再执行安装命令；把“查看名称”和“安装发行版”放进同一句会让读者不清楚先运行哪一条。


只有一两条、读者可以直接理解的短命令，例如 `wsl` 和 `wsl ~`，直接放进正文句子。需要区分用途、强调执行顺序或方便复制时，才保留代码块。面向读者的命令使用完整、可读的长选项（例如 `wsl --list --verbose`），不要使用难以记忆的缩写选项。

删除、重建和重新配置分开表达。「某操作不会影响哪些源文件」这类短结论可以使用 Markdown 引用块。命令块后只保留成功判据和下一步，结果不在正文中重复堆叠；换源这类会改变来源或路径的操作，先说明影响，再给入口和动作。外部链接必须直接支持正文承诺的替代方案，无法核验时删除兜底句，不要求读者到页面中寻找文中没有承诺的内容。代码块中的总注释只说明当前代码块做什么，子注释只补充不明显或容易误用的依赖与用途，均不逐行翻译命令，也不引入正文没有讲过的概念。`{{< include /code/... >}}` 引用真实源码文件，这些文件脱离文档单独阅读，注释按常规写法保持简洁明了，不需要遵守上面这套代码块注释密度要求。

正文默认沿正确流程书写，不把“出现 warning/error 后怎么办”夹在成功路径中。发生诊断时先根据输出中的文件名、行号和原因修复。需要保留的问题说明放入 `## 常见错误`，每个症状使用 `###`；不为此增加 callout 或排错表。编译成功判据、警告策略和选项职责可以写在对应代码块的原生注释中。

# 终端命令与实测输出

本文件是命令、说明与输出展示细则的唯一出处；其他文件只保留指针，不重复展开。

## 命令与结果的顺序

命令块前分别说明执行环境和前置条件，不把权限、系统版本、命令和结果挤在同一句中。推荐使用以下顺序：

1. 说明先决条件和执行位置。
2. 给出可复制的命令。
3. 展示预期结果或真实输出。
4. 说明成功判据和下一步。

有明确先后关系的动作使用有序列表；并列的系统要求、工具要求和注意事项使用无序列表。

## 实测输出

目录、文件名、版本号、工具状态和终端输出应先通过磁盘或命令获取，再写入文档。标记为在 Ubuntu 或 WSL 中运行的只读验证命令，先实际执行，再保留能判断成功的关键行。输出过长时可以筛选版本行、状态行或关键错误，但不能凭空编写结果。

安装、升级和转换发行版等会改变系统状态的命令只展示操作步骤，不在写作过程中重复执行；安装完成后的版本检查可以单独实测并展示结果。环境不可用时只写检查方法，并明确没有实测输出。

不预先编写长段环境校验。逐项运行 `g++ --version`、`cmake --version`、`wsl --status` 之类命令只能证明「此刻命令可调用」，读者已经安装的软件包不会因此变可靠，一旦环境缺失还得重读一遍诊断流程，收益低于成本。安装命令之后直接进入下一步实际操作，报错时由 FAQ 承接诊断。

需要展示工具版本时，把版本信息作为一次实测输出的副产品（例如配置阶段打印的编译器版本），不单独铺陈多条版本命令。

## 命令、说明与输出三分法

命令块只放可复制命令：不加 `$ ` 或 `PS>` 提示符，也不写 `#` 注释。说明命令用途的段落放在命令块之前；输出放在紧随其后的 `text` 块中，命令块与输出块之间只留一个空行。没有结果演示时不添加 `text` 块；多条命令之间同样留一个空行。

按执行环境选择代码块语言：

| 内容 | 代码块 | 约定 |
|---|---|---|
| Linux、WSL 和 Bash 脚本 | `bash` | 只放可敲命令：不加 `$ ` 提示符，不写 `#` 注释；整份脚本的用途注释放在 shebang 与 `set -euo pipefail` 之间 |
| Windows PowerShell | `powershell` | 只放可敲命令：不加 `$ ` 或 `PS>` 提示符，不写 `#` 注释 |
| 真实输出、目录树 | `text` | 不放命令、`$ ` 或 `PS>`，不启用语言高亮 |

提示符和块内注释会让读者分不清哪一行能复制：一个 30 行的块里真正要敲的往往只有三行，粘贴带提示符的行到终端还会直接报错。

```bash
sudo apt install -y build-essential gdb cmake ninja-build clang clang-tidy clang-format
```

命令有输出需要展示时，说明成功判据的正文写在两个块之间，输出进独立的 `text` 块：

```bash
cmake --version
```

```text
cmake version 4.2.3
```

只有一两条、读者可以直接理解的短命令，例如 `wsl` 和 `wsl ~`，直接放进正文句子。需要区分用途、强调执行顺序或方便复制时，才保留代码块。面向读者的命令使用完整、可读的长选项（例如 `wsl --list --verbose`），不要使用难以记忆的缩写选项。

删除、重建和重新配置分开表达；「某操作不会影响哪些源文件」这类短结论可以使用 Markdown 引用块。命令块后只保留成功判据和下一步，结果不在正文中重复堆叠。代码块中的注释只说明当前操作的职责，不逐行翻译命令，也不引入正文没有讲过的概念；声明式文件（CMake、C++）的原生注释规则见 `authoring.md`。

正文默认沿正确流程书写，不把“出现 warning/error 后怎么办”夹在成功路径中。发生诊断时先根据输出中的文件名、行号和原因修复；需要保留的问题说明时，放入专门的排查小节或一个只描述本章最重要风险的 callout。编译成功判据、警告策略和选项职责可以写在对应代码块的原生注释中。

## 诊断与代码块

常见问题中，如果多个命令需要按顺序执行或需要读者复制，使用命令块；一两条无需上下文的短命令直接放入正文。每个代码块前说明目的，后说明成功判据或下一步。

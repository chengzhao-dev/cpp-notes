# 计划产物落盘与完整性

Plan Mode 只在对话中提出计划。用户批准后、首次修改仓库文件前，先把最终计划保存为 Markdown，再按计划执行。

## 执行门禁

计划进入执行前必须依次通过以下门禁：

1. Plan Mode 保持只读，不创建计划文件，不修改仓库，不运行构建、验证或渲染。
2. 最终计划来自 App Server `item/completed` 的 `plan` 项，或完整结束的 `<proposed_plan>` 块。
3. 用户发送新的明确批准消息。批准必须出现在最终计划之后。
4. 收到批准后，先把最终计划保存并校验，再执行计划。

以下信号都不是批准：上下文压缩摘要、自动续跑、任务启动或完成摘要、重复出现的原始需求、计划完成标记、工具建议和模型自己的后续步骤。缺少可核验的批准消息，或协作模式仍为 Plan 时，只继续规划或等待，不写文件、不构建、不渲染。

## 默认路径

- 计划写入 `temp/plans/<日期>-<主题>-plan.md`。
- `temp/` 不提交，计划文件作为当前任务的恢复锚点。
- 文件末尾必须有独立一行 `<!-- plan-complete -->`。

## 中文结构

- Plan Mode 的 `plan` 项、`<proposed_plan>`、宿主 `%USERPROFILE%\.codex\plans\<线程>\<回合>\PLAN.md` 和仓库副本使用同一套中文内容。
- 固定 H2 顺序：`## 摘要`、`## 实施变更`、`## 接口`、`## 验证计划`、`## 假设`。
- `## 验证计划` 末尾必须包含 `### 交付收口`：列出暂存路径组、提交信息、目标分支、推送后 SHA 核对和 CI/Pages 结果；仅做本地任务时明确写“不提交、不推送”。
- 标题、说明和验收项使用中文；代码、命令、路径、API 名保留原文。
- 禁止使用 `Goal`、`Implementation Changes`、`Test Plan`、`Assumptions` 等英文标题，也不得用英文摘要句代替计划正文。

## 来源优先级

1. App Server 最终 `item/completed` 中的 `plan` 项。
2. 完整结束的最终 `<proposed_plan>` 块。
3. 没有前两项时停止落盘，不能从零散消息拼出计划。

不得从 `item/plan/delta`、`turn/plan/updated`、reasoning summary、agent 最终摘要或后续对话改写中重建计划正文。

## 落盘

1. 去掉外层 `<proposed_plan>` 标签，保留标题、列表、表格、代码围栏、链接和确认项。
2. 长计划按 H2 分段写入，避免单次工具调用截断。
3. 写入时不在计划正文中插入进度、哈希或执行备注。
4. 计划修订新建 `-r2`、`-r3` 文件，不覆盖已批准版本。
5. 执行状态另写 `temp/plans/<计划名>-execution.md`，不改写原始计划段落。

## 交付授权与完成

- 用户批准含 `### 交付收口` 的最终计划，只授权该节明确列出的路径组、提交和推送操作，不扩展到 `git add -A`、强制推送、amend、改 remote 或额外分支。
- 成功执行 `check`、`verify`、`render` 或 `build` 只证明本地改动可用，不能替代 commit、push、远端 SHA 和 CI/Pages 核对。
- 远端认证失败、远端领先、推送失败或部署失败时，计划保持未完成；保留本地提交或工作区状态，并报告待处理门禁。

## 校验

写入后立即回读并检查：

- 第一个标题只有一个 H1。
- 计划中的 H2 顺序和数量完整。
- H1 和 H2 使用约定的中文标题，正文不含英文计划标题。
- `## 验证计划` 含非空的 `### 交付收口`，且明确写出本地或远端完成边界。
- 代码围栏成对，表格与列表没有被截断。
- 每个计划章节都有正文或条目。
- 最后一行是 `<!-- plan-complete -->`。
- 回读内容与来源计划一致，不能只检查文件非空。

任一检查失败时停止执行，重新从最终计划项生成新文件。不得在残缺计划上继续修改仓库。

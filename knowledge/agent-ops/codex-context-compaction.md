# Codex 上下文压缩的触发方与可配置项

> 本文件记录 Codex 宿主侧上下文压缩（compaction）由谁触发、agent 能做什么、哪些配置项真的可选。
> 它是这块领域事实的唯一出处。`.agents/skills/agent-ops/references/repository-structure.md` 只保留压缩前后的执行纪律，
> 不复述机制。结论来自本机 `codex-cli 0.153.4` 的可复现核验，换版本时需重新实测。

## 压缩由宿主触发而不是 agent

### 三类触发入口的归属

1. 自动触发：对话上下文接近宿主的自动压缩阈值时，由运行时发起一次总结并替换历史窗口
2. 用户手动触发：交互界面里的压缩指令，由用户在回合之间主动发起，agent 无法代为按下
3. agent 侧：本会话的工具清单里没有任何压缩入口，因此「让 agent 在上下文吃紧时自行压缩」是无效描述
4. 每次压缩都会在会话落盘里开启一个新的上下文窗口，旧窗口留下可核对的窗口编号与替代历史
5. 压缩是有损摘要：细节以替换后的摘要为准，工具状态与文件内容仍应回读磁盘确认

### 为什么 agent 侧不该承诺压缩

1. 阈值、时机与摘要算法都在宿主运行时手里，规则里写「约 70%–80% 时压缩」无法被执行也不可控
2. agent 唯一能做的是让压缩损失变小：把进度落盘、把结论写成可复跑的命令，而不是留在对话里
3. 宿主在压缩后会把摘要连同工具状态交回同一个线程，因此不完整的中间态会被原样带进下一轮

## 可选的宿主侧配置项

### 控制压缩时机

| 配置键 | 作用 | 取值 |
| --- | --- | --- |
| `model_auto_compact_token_limit` | 自动压缩的令牌阈值 | 正整数令牌数 |
| `model_auto_compact_token_limit_scope` | 阈值统计范围 | `total` 或 `body_after_prefix` |
| `model_context_window` | 模型可用上下文窗口 | 正整数令牌数 |

1. 阈值调小：压缩更早发生，单次请求更省令牌，但摘要次数增多、细节丢失更快
2. 阈值调大：保住更多原始历史，代价是每次请求携带的上下文更长、更慢也更贵
3. `total` 按整段历史计量，`body_after_prefix` 只按固定前缀之后的增量计量，两者对同一数值的实际效果差别很大
4. 这些键写在宿主的用户级配置里，属于本机行为调优，不应写进仓库随库分发

### 控制压缩摘要的写法

1. 压缩提示词可由宿主配置项替换，官方描述为「压缩对话时使用的提示词」，用于决定摘要保留什么
2. 宿主还提供压缩前后的生命周期钩子，可在压缩前落盘状态、在压缩后重新读取作用域
3. 钩子属于宿主能力而不是仓库规范，启用前需要用户确认，不在项目文档里给出可直接运行的配置

## 压缩后的可执行纪律

### 让交接不依赖对话记忆

1. 每轮只推进一个可验证的子目标，收尾时把状态写进版本库可见的文件
2. 可复现的事实（版本号、目录结构、链接可达性、索引条数）在需要时重新实测，不从摘要里的旧结论取值
3. 发现历史只剩摘要时，先重读任务作用域与工作区状态确认边界和已完成项，再继续编辑
4. 每轮结束前用一次统一校验收口，避免把未验证的中间态留给下一轮
5. 计划任务先读取已校验的 `temp/plans/` 计划文件，再结合工作区状态继续；计划文件不能替代最终代码与检查结果

### 摘要不是执行授权

1. 自动压缩后的续跑仍属于原任务，不会退出 Plan Mode，也不会自动获得写文件、构建或渲染的权限
2. 摘要中的“待执行”“下一步”和“可选动作”只描述计划状态，不是用户批准
3. Plan Mode 下收到续跑时，先恢复目标、约束和当前计划，再继续只读调查或完善计划
4. 只有最终计划之后的新用户消息明确批准执行，才能进入落盘、修改和构建阶段

### 压缩质量的已知代价

1. 多次连续压缩会叠加摘要损失，长任务更应尽早开新线程而不是持续压缩同一线程
2. 摘要里的「已完成」不等于磁盘上的已完成，编辑前必须回读目标文件确认

# C++ 章节与开发环境写作案例

## 导语案例

引言按“上一章结果 → 为什么需要这个环境 → 本章动作路径”推进，一句话只做一个动作。不要重复后文的任务条件、命令和完成结果；页面块序列以 `cpp-quarto-chapter-pattern-v1` 为准，写法规则见 `quarto-docs` 的 `cpp-chapter-writing` reference。

```text
Hello, World! 是大多数人的第一个 C++ 程序。
它用最少的代码走通“写出源码、编译、运行、看到输出”这条流程，也验证上一章的工具是否可以工作。
本章先用 g++ 直接构建，再用 CMake 管理构建，两种方式最后都会运行出 Hello, World!。
```

## 环境章引言与 WSL2 案例

环境章节的引言只建立“Windows 不能直接执行 Linux 教程，WSL2 提供 Linux 环境，本章默认使用 Ubuntu”这一层认识。读者此时不需要知道具体编译器、构建工具、终端和编辑器的名字；这些对象在对应任务中第一次出现时再解释。引言中的事实要体现因果或推进关系，例如先说明 Linux 教程无法直接在 Windows 执行，再引出 WSL2 和 Ubuntu，不能把几个正确但彼此孤立的句子并排堆放。Windows 版本、BIOS/UEFI 和软件源要求放在对应任务中，引言不重复。环境基线只在本章展开，后续章节链接回来并声明新增前提。入门章节引言控制在约 80–120 个中文字符，只承接上一章并引出当前内容，不介绍章节流程。

标题使用简短任务名，删去可以下移到首句或解释段的限定条件。例如“启用 WSL2 并安装 Ubuntu”可以收敛为“安装 WSL2 和 Ubuntu”，“安装构建、调试与诊断工具”可以收敛为“安装工具链”。当多个子任务共享同一个环境准备阶段时，可以用 `## 准备 Linux 开发环境` 统摄 `### 安装 WSL2 和 Ubuntu`、`### 安装其他发行版` 与 `### 安装 C++ 工具链`。工具链仍有自己的命令和可见结果，但三者共同交付可继续构建 C++ 程序的 Linux 环境，作为同一环境准备阶段的子任务能避免父级标题的阶段信息被拆散。父标题只交代阶段或范围，不写“本节安装……”的复述导语，也不能只是页面标题的同义改写。症状标题同理，只保留“虚拟机平台未启用”“找不到命令”这类核心故障，补充条件放进正文。

安装任务以“下一步可以继续”作为结果，只有后续操作确实依赖某项可观察结果时才补判据。账号创建、密码不回显属于首次启动阶段，提示符成功判据和后续终端范围属于进入 Ubuntu 后的结果，两组状态之间拆段，不要把整条流程压成一个长段。

提示符同时承担成功判据、后续终端范围和界面术语入口，而且之后没有必经动作，因此正文用“请对照下面的格式，确认是否已经进入 Ubuntu，并了解后续命令的执行位置”建立检查动作，Callout 首句直接给出“看到类似 `user@host:~$` 的提示符，就说明已经进入 Ubuntu”，再把后续范围和三项组成放进同一个尾置结果型 `note`。这样既不重复同一结论，也不再把提示框压成脚注；若提示符之后还要读者执行命令或据此修复，则应回到普通分层，把判据留在正文。

安装其他发行版单独使用 `###`，并先说明继续使用默认 Ubuntu 时可以跳过，避免读者把可选路径误当成必经步骤；这里不引入切换默认发行版。要安装时，先给出 `wsl --list --online`，再明确从输出复制目标发行版名称、原样替换 `wsl --install -d <发行版名称>` 中的占位符，最后执行安装命令。新手容易混淆发行版名称与友好名称，也可能修改名称的大小写或空格；指出取值来源并保留两个可复制代码块，可以减少误填和“记下后再处理”的猜测。失败时在 `常见错误` 中按三步诊断流展开：标题后的首句同时说明触发条件与可观察现象，再依次给出定位、修复和验证动作。具体结构与取舍见 `cpp-quarto-troubleshooting-flow-v1` 和 `cpp-quarto-section-focus-density-v1`。

## 从环境到首个程序的连续路径

相邻入门章节不应各自从零开始。环境章已经把读者带到 Ubuntu 提示符并安装工具链，首个程序章只承接这个状态，改为说明读者应先打开完整示例工程并位于工程根目录。若前章没有提供 Git 或下载步骤，就不能为补齐叙事临时加入新的必经命令，否则会把未满足的前置条件藏进成功路径。

同一 `Hello, World!` 源码依次经过目录树、源码阅读、`g++`、CMake 和脚本，读者才能看出变化只来自构建方式。目录树先为“工程根目录”提供位置，真实源码建立观察对象，`g++` 先给最短路径，CMake 再增加配置与构建规则；脚本只是 CMake 路径的封装。若让不同路径各自使用不同的源码、目标名或输出目录，读者会把差异误归因到程序内容。

环境安装、直接编译和 CMake 配置的输出会受系统版本和路径影响，全文不应把一次完整终端输出当作契约。优先让读者观察提示符、关键输出行、退出码、生成的 `build/bin/app` 或最终的 `Hello, World!`。脚本会额外打印阶段标题和 CMake 输出，因此只承诺输出包含或末行显示程序结果，不伪造一段只有程序输出的终端记录。

## 删改后的环境动作衔接案例

删除安装步骤之间的衔接句，可能同时删除后文所需的状态变化原因，让新手看不懂后续动作为什么出现。WSL2 安装命令改变的是 Windows 组件状态，`wsl --install` 完成后系统可能要求重启，重启是为了让组件生效，之后才进入首次启动 Ubuntu 的流程。若只保留“重启 Windows，然后首次启动 Ubuntu”，新手会把重启理解成突然插入的额外要求。

```text
命令执行完成后，按提示重启 Windows，让新启用的 WSL2 组件生效。重启后首次启动 Ubuntu，按提示创建 Linux 用户名和密码。
```

压缩环境章时先确认后文是否依赖被删句。若依赖，保留“触发时机 → 状态变化及原因 → 可观察结果 → 下一步”的最短闭环；删除后还要回读切口，不能留下悬空的“然后、因此、此时、重启、再次”。短过渡句承担因果关系时不是冗余。

## 官方文档与项目动作的边界

WSL 和发行版都有持续更新的官方安装与配置教程。把版本差异和完整 GUI 操作留给官方页面，能避免笔记同时维护过期步骤；本章只保留读者完成当前 C++ 任务时必须知道的入口和最小项目动作。可选终端与编辑器接入不属于本章主线，不为它们增加独立 `##` 或排错分支。

## 环境章的收尾与排错

配置型环境章的回顾目标是确认环境状态，不是考查抽象概念。成功路径已经在各任务末尾给出判据，因此回顾只保留一句状态总结和下一章入口，不再追加“为什么”类问题。失败分支则服务于回到主线的读者。每个故障先用一句话同时说明触发条件与可观察现象，具体操作结构见 `cpp-quarto-troubleshooting-flow-v1`。

安装工具时，逐包展开职责会让命令淹没在说明中，读者无法快速识别当前操作。上游页面已经维护版本差异时，正文只给入口和当前动作。换源说明需要先消除“换源等于升级版本”的误解，再承接更新动作。具体命令注释与成功判据格式见标识 `cpp-quarto-troubleshooting-flow-v1` 所指向的写作规则。

## 工程与命令案例

目录树、代码块、构建命令和生成结果必须使用相同文件名。目录树行尾注释承担路径用途，正文只补充代码无法直接说明的前提、因果、边界和验证。具体规则见 `cpp-quarto-project-tree-diagram-focus-v1`。

CMake 任务可以在同一 `##` 下分为“配置并构建”和“用脚本一键运行”两个 `###`。命令、输出、成功判据和按症状排错以 `quarto-docs` 的 `terminal-validation` reference 为唯一出处。

Quarto 官方入门教程通常先给安装或运行的最小路径，再展示可见结果，最后才进入参数和扩展主题。C++ 入门页也应先提供完整示例工程和可运行结果，再展示目录树、选项与替代路径。卡片不得把后续计划写成本页能力，目录树不得把生成目录与源码并列为初始文件，便利脚本也不能被描述成与 `g++`、`CMake` 并列的第三种构建方式。

参数补充放在主线闭合之后，读者才能先复制执行，再回看选择依据。清理目标和移走构建目录属于不同动作，不应塞进同一个代码块。

## 源码阅读案例

如果真实源码的注释已经能说明关键符号，读者直接阅读源码和注释即可，不再增加一张重复解释的导览表。正文只需说明程序的作用、意义和阅读目标；只有当代码或注释仍不足以辨认观察对象时，才补充符号导览。

## 封装脚本案例

封装脚本让读者一键跑通，代价是他不知道脚本内部做了什么，出错时无法定位到某一步。直接展示真实脚本或引用仓库文件，让注释承担逐段说明；正文只概括脚本的职责、执行位置和失败行为，避免再用文字逐条复述命令。

## 构建方式比较案例

多种做法并存时，读者的问题不是“怎么写命令”，而是“现在该用哪个”。只有确实需要横向比较多个属性时才用对照表，否则用正文直接给适用场景与代价，并放在主线跑通之后。g++ 与 CMake 两条路径使用同一标题模式，避免“编译、配置、构建”混在一个标题里。

## 命令判据与破坏性操作案例

配置和构建输出会随版本、路径和缓存状态变化，因此案例只保留稳定的关键行、产物或退出码，不把某次完整输出当契约。不可逆命令需要先出现可逆替代。具体判据与操作格式见 `quarto-docs` 的 `terminal-validation` reference。

排错条目按现象使用 `###`，让目录负责故障导航。步骤顺序的完整设计理由见 `cpp-quarto-troubleshooting-flow-v1`。

## 正确流程与诊断说明案例

教程正文默认沿正确流程推进。失败分支夹进首次成功路径会打断读者对当前状态的判断，因此诊断内容集中在专门区域。

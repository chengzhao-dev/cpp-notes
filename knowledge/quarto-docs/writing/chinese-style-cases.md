# 中文技术写作的段落与措辞案例

本文件保存不佳表达与改写对照。可执行规则见 `quarto-docs` 的 `writing-principles` reference，本文件不维护第二套规范。

## 段落与代码块闭环案例

一个段落只推进一个对象：说明条件、执行动作、给出结果，再进入下一步。代码块前说明为什么执行，代码块后说明看到什么算成功。

```text
代码块前：进入示例目录，准备编译 main.cpp。
代码块后：成功后生成可执行文件，下一步运行它。
```

环境描述不要在一句话中同时引入 Windows、WSL2、Ubuntu、编辑器和构建工具。先说明宿主与 Linux 环境的关系，再介绍当前步骤需要的工具。

## 长句与连接关系案例

连接词必须表达真实因果、时序、转折或条件。一个句子出现三个以上动作、多个“并且”或多个括号时考虑拆分，并保留明确主语。

```text
不佳：完成 A 后通过 B 使用 C，并根据 D 判断 E，最后处理 F。
改写：完成 A。接着使用 B 执行 C。根据 D 检查结果，满足条件后处理 F。
```

## 分号与句长案例

```text
不佳：先执行 A；再执行 B；完成后检查 C，不通过时回到上一步。
改写：执行 A，再执行 B。完成后检查 C。不通过时回到上一步。
```

需要一句话交代多个条件与同一结果的对应关系时，拆开会反复出现同一个主语，读者反而要在几个短句之间来回拼接，这时保留长句更清楚。

## 措辞替换案例

| 不佳表达 | 改写 |
|---|---|
| 对文件进行修改 | 修改文件 |
| 如果……的话 | 如果……，或……时 |
| 其实/简单来说/完全/非常/特别 | 删除，不保留无信息修饰 |
| 吃透/讲清/彻底理解 | 改成可观察的验证结果 |
| 错误被返回 | API 返回错误 |
| 再用 `g++` 对照直编 | 再用 `g++` 直接编译这个单文件程序 |

## 指代与验收案例

已知对象名称时直接复用对象名。`这个程序只有一个源文件` 应改为 `Hello, World! 示例程序只有一个源文件`。验收句要指向可观察结果，例如 `看到 Hello, World! 后，就完成了本章的实践目标`，不要写 `本章就完成了`。

## 术语节奏案例

首次出现时给中文名称与英文检索词，后续固定一种称呼。普通概念不加行内代码，命令、路径、文件名、关键字、API 和配置键使用行内代码。标记边界见 `cpp-quarto-inline-code-boundaries-v1`。

## 读者引导与维护信息分开案例

作者如何检查磁盘、筛选目录树或安排写作不属于读者路径。把“根据实际目录筛选出的教学视图”写进章节，会让读者误以为需要理解作者的整理过程。正文用一句话同时交代对象和动作，例如“下面的目录是本章示例的文件清单，所有命令都在该工程根目录执行”，不把两个短句拆开连续堆放。

目录树行尾注释已经给出文件职责，树后再逐项说明维护归属只是换一种形式重复。若当前操作需要判断“哪些能改、哪些由工具生成”，保留一张归属表，其余情况删除。目录树依据见 `cpp-quarto-project-tree-diagram-focus-v1`。

## 连续短句与注释职责案例

把同一对象拆成“目录如下。命令都在这里执行。”会制造停顿，读者需要在两个短句之间重新拼接关系。可以直接写成一个动作句：“下面的目录是本章示例的文件清单，所有命令都在该工程根目录执行。”同理，换源原因、版本差异和配置路径差异属于同一决策，应合并成一段；换源只会改变下载来源和速度，不会改变发行版版本。先说明这一影响，再承接更新动作，读者才不会把换源误解为升级版本。修复段还要点名定位中的具体对象，不能写“缺失的功能”这类含糊指代。

安装命令逐包展开职责会把操作埋在说明里，因此本案例只保留“代码块负责动作、正文负责当前目标”的职责判断；格式细则见 `terminal-validation` reference。

## 长段拆分与 Callout 下沉案例

一个段落同时交代多个动作、验收结果和可跳过说明时，读者无法一眼判断哪些内容属于当前主线。先保留完成当前任务所需的信息，再将只帮助理解、不影响继续操作的细节放到末尾 Callout。

```text
不佳：
命令执行完成后，按提示重启 Windows，让新启用的 WSL2 组件生效。重启后首次启动 Ubuntu，按提示创建 Linux 用户名和密码。输入密码时不会显示字符，这是正常现象。出现类似 `user@host:~$` 的提示符，说明已经进入 Ubuntu，后续 `bash` 命令都在这个终端中执行。

::: {.callout-note title="提示符的组成"}
`user` 是用户名，`host` 是主机名，`~` 是当前用户的主目录。
:::

改写：
命令执行完成后，按提示重启 Windows，让新启用的 WSL2 组件生效。重启后首次启动 Ubuntu，按提示创建 Linux 用户名和密码。输入密码时不会显示字符，这是正常现象。

创建账号后，终端会显示提示符。请对照下面的格式，确认是否已经进入 Ubuntu，并了解后续命令的执行位置。

::: {.callout-note title="提示符与终端范围"}
看到类似 `user@host:~$` 的提示符，就说明已经进入 Ubuntu。后续 `bash` 命令都在这个终端中执行。

- `user` 是用户名。
- `host` 是主机名。
- `~` 是当前用户的主目录。
:::
```

判断依据是段落是否混入多个职责，不是字数。账号创建和密码不回显属于首次启动阶段，提示符成功判据和后续终端范围属于进入 Ubuntu 后的结果。提示符之后没有必经动作，精确判据又需要与三项组成一起解释，因此正文用“请对照下面的格式确认是否已经进入 Ubuntu，并了解后续命令的执行位置”建立检查动作，Callout 首句直接兑现所见结果。正文不复制完整判据，Callout 也不再重新起句。长段拆短不等于把提示框压成脚注，符号含义也不要和观察对象拆成两处；若后续仍要根据提示符继续操作，判据应留在正文。完整边界见 `cpp-quarto-section-focus-density-v1`。

## 标题导语与代码块前标点案例

`##` 下不强制写导语。标题已经说明任务时可以立刻给出动作，也可以直接进入第一个 `###`。只有导语补充任务顺序、前置条件、范围或标题没有表达的结果时才保留，不能只把标题换一种说法。

```text
重复：
## 建立 Linux 开发环境
本节安装 WSL2、Ubuntu 和 C++ 工具链，得到后续示例使用的 Linux 开发环境。

改写：
## 安装 WSL2 和 Ubuntu
以管理员身份打开 Windows PowerShell，执行下面的命令安装 WSL2 和默认的 Ubuntu 发行版。
```

代码块前不固定使用冒号。完整动作句仍是句子，用句号收束。只有“如下、以下、例如”已经明确把代码或输出作为后续内容时才用全角冒号。

```text
动作句：
在 Ubuntu 终端执行下面的命令，更新软件包索引并安装工具链。

结果引导：
程序输出如下：
```

## 代码标题与正文分工案例

代码块标题已经写明运行环境或文件来源后，正文再写“下面是一段 Bash 命令”只会重复视觉上已经存在的信息。正文应直接说明当前动作和观察目标，例如“在工程根目录配置并构建示例”或“运行程序后应看到下列输出”。若需要说明权限、目录和安全边界，应在正文中写清，不能用标题替代。

```text
重复：下面是一段 Bash 命令，用来配置 CMake 工程。
改写：在工程根目录配置 CMake 工程。

重复：下面是 main.cpp 的完整源码。
改写：先通读源码，再让编译器把它变成可执行程序。
```

标题负责“来自哪里”，正文负责“现在做什么、怎样算成功”。两者各有一个权威位置，读者既不用从上下文猜环境，也不会读到两遍相同的定位信息。

## 项目自称案例

“本书”把个人维护的教程误写成正式出版物，也与仓库实际形态不符。项目自称统一为“这份笔记”，例如“要按这份笔记里的 Linux 教程编译 C++ 程序”。技术含义不变，表述更符合项目性质。

## 文件名密度案例

读者已经知道被处理的是生成物目录时，逐个说明“不会影响 `main.cpp`、`CMakeLists.txt` 和 `build-and-run.sh`”没有增加可执行信息。一个段落只保留影响当前决策的一两个标识，其余换成“源码和构建配置”“其他脚本文件”这类集合称呼。

判断方法：读者不需要这个名字也能完成当前步骤时，名字就是噪声。目录树已经逐项交代过职责的，正文不再重复点名。

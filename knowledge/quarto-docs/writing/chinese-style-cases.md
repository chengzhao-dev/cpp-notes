# 中文技术写作的段落与措辞案例

## 段落与代码块闭环

一个段落只推进一个对象：说明条件、执行动作、给出结果，再进入下一步。代码块前说明为什么执行，代码块后说明看到什么算成功。

环境示例不要在一句话中同时引入 Windows、WSL2、Ubuntu、编辑器和构建工具。先说明宿主与 Linux 环境的关系，再介绍当前步骤需要的工具。

```text
代码块前：进入示例目录，准备编译 main.cpp。
代码块后：成功后生成可执行文件；下一步运行它。
```

## 长句与连接关系

连接词必须表达真实因果、时序、转折或条件。一个句子出现三个以上动作、多个“并且”或多个括号时拆分，并保留明确主语。

```text
不佳：完成 A 后通过 B 使用 C，并根据 D 判断 E，最后处理 F。
改写：完成 A。接着使用 B 执行 C。根据 D 检查结果，满足条件后处理 F。
```

## 分号与句长

正文不使用分号“；”。并列的分句改用逗号，语义独立的分句改写成两个句子。一个句子只推进一个动作或一个结论，读者不需要回读上一句就能理解当前这句。

```text
不佳：先执行 A；再执行 B；完成后检查 C，不通过时回到上一步。
改写：执行 A，再执行 B。完成后检查 C。不通过时回到上一步。
```

长句并非一律要避免。需要一句话交代多个条件与同一结果的对应关系时，拆开会反复出现同一个主语，读者反而要在几个短句之间来回拼接，这时保留长句更清楚。判断标准是拆完之后理解成本有没有上升。

规则的适用范围是正文、标题、表格和列表。行内代码和代码块内部照抄真实语法，不做改写。带命令前缀的列表项里，反引号闭合之后的文字仍属于正文，继续使用正常标点。把分号换成逗号和句号，是因为分号在中文技术文档里没有稳定的使用习惯，读者会把它当成句子结束，也会因为前后分句同等重要而判断不出主线，短句号加逗号的分层更贴合中文的阅读节奏。

## 措辞替换

删除不增加信息的“其实”“简单来说”“完全”“非常”“特别”。将“对文件进行修改”改为“修改文件”，将“如果……的话”改为“如果……”或“……时”。

避免“吃透”“讲清”“彻底理解”等无法由正文验证的承诺。系统行为明确主语，例如“API 返回错误”，不要写“错误被返回”。

## 术语节奏

首次出现时给中文名称与英文检索词，后续固定一种称呼。普通概念不用行内代码。命令、路径、文件名、关键字、API 和配置键使用行内代码。多行可复制命令和完整示例使用标明语言的代码块。

## 读者引导与维护信息分开

正文服务读者当前要完成的动作，作者如何检查磁盘、筛选目录树或安排写作不属于这条路径。把“根据实际目录筛选出的教学视图”写进章节，会让读者误以为需要理解作者的整理过程，反而削弱“接下来做什么”的信号。这类判断留在 `quarto-docs` 的目录树 reference。正文只用一句话引出下一步，例如“工程目录如下。后面的命令都在这个目录里执行。”

目录树中的行尾注释已经给出文件职责，树后再写一段“哪些文件需要维护、哪些文件由工具生成”，只是把同一信息换一种形式重复一次。除非这句话直接影响当前操作，否则删除它。若确实需要边界提醒，也只保留一句，不逐项复述。

## 段落里的文件名密度

一个段落同时点名四五个文件和脚本时，读者的注意力会从“这一步要做什么”转移到逐个核对名字，段落里最高优先级的信息被平均化。文件名的价值在于可复制和可定位，而不在于出现次数。读者已经知道被删除的是生成物目录时，逐个说明“不会影响 `main.cpp`、`CMakeLists.txt` 和 `build-and-run.sh`”没有增加可执行的信息。

因此一个段落只保留影响当前决策的那一两个标识，其余换成“源码和构建配置”“其他脚本文件”这类集合称呼。判断方法只是反问一句，读者不需要这个名字也能完成本步吗？能，名字就是噪声。目录树已经逐项交代过职责的，正文不再重复点名，只引用集合概念。

这些是中文表达和读者感受的依据。章节导语与任务序列见 `cpp-quarto-chapter-pattern-v1`，目录树边界见 `cpp-quarto-project-tree-diagram-focus-v1`，句内连接和长句拆分仍以本文件前面的案例为准。

# 常见错误的三步诊断流

## Quarto FAQ 的边界

Quarto FAQ 用问题标题和短答案直接回应读者，入口清楚且不重复背景。本站的“常见错误”对应按顺序执行的失败路径，因此保留症状标题和“定位 → 修复 → 验证”，只借鉴 FAQ 的直答节奏：标题后立即给出触发条件与可观察现象，步骤标题使用动作，不先写泛化铺垫。若问题与故障无关，应进入专门说明或正文，而不是扩展成第二个 FAQ 区。

## 结构边界

### 三级关系如何分工

`## 常见错误` 是失败路径的入口，`###` 是读者可以直接检索的故障症状，步骤列表是故障内部的执行顺序。三者分别承担导航、识别和操作，不把每个操作阶段再升级为标题。这样既保留右侧目录的定位价值，也避免目录被重复的阶段标签占满。

### 现象为什么放在标题后

故障标题只保留核心症状，标题后的第一句补充触发命令、错误表现和必要环境。读者扫描目录时先找到症状，打开条目后立即确认自己是否遇到同一问题，不需要在重复的“现象”标签中寻找判断依据。

## 三步顺序

### 定位、修复和验证的职责

定位只收集能缩小范围的最小证据，修复使用定位得到的具体对象，验证给出可观察结果。三步不是固定的措辞装饰，而是故障处理的因果链：没有定位结果就不应猜测修复对象，完成修复也不能代替确认系统已经恢复。

### 有序列表为什么承载主线

定位、修复和验证具有先后依赖，使用有序列表可以把执行顺序直接呈现给读者。多个原因可以并列检查时，在对应步骤下使用无序列表。只有顺序影响结果时才继续使用有序列表，避免把信息分类误写成伪流程。

### 步骤标签和故障入口如何接力

有序列表的步骤名和说明承担不同职责。步骤名若与说明同权，读者扫视时只能看到三段等权文字。只把短动词短语加粗，可以先读完三步，再按需进入说明，也不会像标题那样形成额外层级或污染目录。

故障引言负责交代触发条件、可观察现象和恢复路径，列表负责执行，验证末尾负责把读者送回主线。引言复述每一步会让列表失去增量。验证只写“不再报错”而不说明后续位置，又会让恢复后的下一步悬空。例如软件源修复完成后，应回到安装 C++ 工具链的位置继续操作，而不是让读者停在一个孤立的成功判据上。

## 元素选择

### 命令和结果如何就地出现

命令、输出与成功判据需要让读者分清“输入、观察、判断”三种角色。具体块格式见 `quarto-docs` 的 `terminal-validation` reference，本文件只解释为什么三者不能混在同一个视觉块中。

### 代码型步骤为什么不能混排

开发者按“定位 → 修复 → 验证”的固定形状扫描故障页。两步给出代码块、另一步只写一句说明时，读者需要重新判断后者是没有命令、遗漏命令，还是应该回到上一节执行。包含命令的步骤使用同一种块结构，可以保留步骤并列关系，也让复制和验证动作在同一位置找到。

### 为什么不用排错表和自定义容器

表格适合横向比较短属性，不适合承载需要顺序执行的长动作。自定义容器的视觉效果依赖主题 CSS，且不能获得 Quarto 内置 Callout 的稳定语义。原生标题、段落、列表和代码块在不同页面和视口下更容易保持可读与可验证。

## 边界与安全

### 多分支故障如何展开

一个症状包含多个明显原因时，先在定位步骤列出分支，再让每个分支指向对应修复动作。分支数量已经形成独立任务时，应拆成多个 `###`，否则单个故障条目会失去快速判断的价值。

### 危险操作如何保持可恢复

删除、覆盖或重建动作仍遵循可逆替代、影响范围、恢复方式和验证结果四项约束。三步诊断流只改变信息组织，不降低破坏性操作的说明要求。安全边界应放在对应步骤附近，不用提示框隐藏必经动作。

## CMake 缓存排错案例

### clean 与重新配置为什么不能混用

clean 与重新配置控制的是不同对象，混用会让读者误以为旧缓存已经消失。CMake 层面的因果与诊断顺序属于 `cpp-content` 领域，见 `cpp-tooling-build-chain-v2`。

### 诊断时为什么保持 Debug

排查构建失败时同时切换构建类型，会把工具链或缓存问题与优化、调试信息差异混在一起，无法判断究竟是哪项变化修复了问题。具体排查顺序见 `cpp-tooling-build-chain-v2`。

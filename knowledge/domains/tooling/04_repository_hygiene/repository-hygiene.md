# 仓库一致性与分支保护依据

> 本文件记录跨平台仓库卫生措施的成因与取舍，是这块领域知识的唯一出处。
> 具体命令序列与禁止事项由 skill 侧 `github-ops/references/git-workflow.md` 承载，不在此重复。

## 行尾与编码的归一化

### 归一化策略要写在版本库里

1. 行尾由谁决定是三件事的合力：仓库内的属性文件、每台机器的客户端配置、检出时所在平台
2. 只有客户端配置时，同一份文件在 Windows 与 Linux 上会各自变成不同字节，差异以整文件重写出现在 diff 里
3. 属性文件进版本库后策略随仓库走，任何机器与流水线检出结果一致，这是跨平台协作的唯一可靠载体
4. 统一为换行符的动机有两个：流水线跑在 Linux，以及差异噪音会让代码检查工具对整文件报错
5. 归一化只处理文本，图片与字体等二进制必须显式声明为二进制，否则内容会被改写而损坏
6. 依赖 Windows 换行符的工具脚本要保留原行尾，这属于例外而不是疏漏

### 策略变更要一次性落地

1. 归一化规则改变后，存量文件的索引内容仍按旧行尾存储，工作区却已按新规则转换，两者不一致
2. 用重规范化把所有存量文件一次性对齐，代价是一次体积很大的提交，收益是此后不再出现行尾型差异
3. 分批落地会让每次提交都混入行尾改动，掩盖真实变更，因此宁可单独做一次

## 忽略规则的集中与可验证性

### 规则来源必须唯一

1. 忽略规则分散在多个子目录时，判断某路径是否入库需要遍历整棵目录树，审计成本随目录深度上升
2. 集中在根文件让规则成为一份可通读的清单，嵌套目录只允许出现「反过来强制纳入」的特例
3. 是否被忽略应当可查询而不是靠记忆：忽略检查命令能给出命中规则的文件与行号
4. 产物目录、缓存目录与本机配置一旦入库，clone 体积与 diff 噪音同时失控，且本机配置会在别人机器上产生错误行为

### 本机信息与可复现信息的边界

1. 解释器绝对路径、凭据、个人配置属于本机信息，正确做法是不入库并在文档里写明重建协议
2. 判定标准是「换一台机器这条内容还成立吗」，不成立就不进版本库
3. 把本机路径写进仓库文档还会泄露个人目录结构，属于不必要的信息暴露

## 分支拓扑与保护

### 远端分支数量是约束而不是习惯

1. 源码分支与产物分支分离后，远端只需要这两个分支，其它分支的存在没有下游消费者
2. 多余的远端分支会被误认为站点来源或发布通道，排查时增加无效分支
3. 用仓库级规则禁止新建远端分支比口头约定可靠，紧急场景可临时关闭该规则
4. 本地临时分支不受影响，实验完合并后删除即可，不需要推到远端

### 保护规则要覆盖删除与改写

1. 源码分支禁止强推：强推会让已部署的产物与源码历史分叉，站点内容无法对应任何一次提交
2. 源码分支禁止删除：它是产物分支与历史记录的唯一基准
3. 产物分支禁止删除：删掉即站点消失，且恢复需要一次完整渲染
4. 产物分支只由自动化写入，人工推送会在下一次部署时被孤立提交整体覆盖，形成「推上去又不见了」的假象

## 提交切分的依据

### 按可独立回滚的边界切分

1. 分组的判据是「出错时希望回滚到哪」，而不是文件类型是否相同
2. 同一行为变更跨多个文件时合并成一组，拆开反而制造不可运行的中间状态
3. 提交信息前缀的作用是让读者不看 diff 就能判断影响面与是否需要跑检查
4. 一次任务通常三到五组，超过说明改动本身该拆成多个任务；为拆而拆会让回溯成本高于收益

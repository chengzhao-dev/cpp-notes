# C++ 构建与工具链决策依据

> 本文件回答“为什么这样配”，是这块领域知识的唯一出处。写给读者的正文约定与命令块格式由 skill 侧的 references/cpp/toolchain.md 承载，不在此重复。

## 工具链为什么是教学内容的一部分

### 编译选项决定 bug 能否在开发期暴露

1. C++ 编译到机器码，标准选择与警告等级直接决定哪些错误编译器会替你抓住
2. 大量未定义行为、内存泄漏与数据竞争只在高优化级别下暴露，-O0 测试通过不代表正确
3. 同一份代码在 GCC、Clang、MSVC 下结论可能不同，跨编译器验证能揪出非标准写法
4. 现代工程把警告当错误（-Werror），并用 sanitizer 在测试阶段兜底，比线上崩溃便宜得多
5. 本仓库默认环境是 Windows 上的 WSL2（GCC/Clang/CMake），MSVC 仅作对照，不要求读者手上有 MSVC

### 最小成功路径优先

1. 工具链内容的第一条路径应为：确认编译器存在，编译并运行一个程序，再引入构建系统
2. 每组工具先回答它解决什么问题，再给参数；参数表放在决策之后，不做开场
3. 安装与验证是两件事：安装只说明动作，是否可用由版本查询单独确认
4. 源码、构建目标与运行输出必须互相对得上，不能让示例代码与展示结果不一致
5. 工具不可用时如实说明限制，不伪造版本号与成功输出

## 编译标准与警告

### 标准选择

1. 入门与示例统一 C++20，避免同一本书混用标准导致读者无法判断哪些特性可用
2. 只追新特性时才用实验性开关，代价是可移植性与工具链支持都不稳定
3. 三家编译器开关写法不同：GCC/Clang 用 -std=c++20，MSVC 用 /std:c++20，写错直接报错
4. 标准必须由构建系统固定，不能依赖编译器默认值，否则换机器行为就变

### 警告分级

1. -Wall -Wextra 是基线，覆盖未初始化、签名不匹配、变量遮蔽等高频问题
2. 入门示例建议 -Werror：把以后再看的警告变成必须处理，代价是首次编译红灯较多
3. -Wpedantic 检查非标准扩展，与第三方头文件同用时会被外部警告淹没，应按需开启
4. MSVC 对应 /W4，它的警告集合与 GCC/Clang 不重合，不能用 MSVC 没报警证明代码干净
5. 警告的价值在于覆盖你没想到的情况，因此不建议为了清静而整批关闭

## 调试与优化级别

### 级别选择

1. Debug 构建用 -O0 -g：保留变量与行号对应关系，优化会重排、内联、消除变量，断点会跳
2. Release 构建用 -O2；-O3 需谨慎，更高的内联与向量化不一定更快，且会放大未定义行为的影响面
3. 性能测量必须在发布级别做，-O0 下的结论通常只反映编译器的保守策略
4. sanitizer 与高优化不要混用：优化会消除 sanitizer 依赖的边界信息与调用栈

### Sanitizer 选择

1. AddressSanitizer 覆盖越界、use-after-free、double free 与泄漏，是内存问题首选
2. UndefinedBehaviorSanitizer 覆盖有符号溢出、空指针解引用、对齐错误、非法转型
3. ThreadSanitizer 覆盖数据竞争，开销显著且与 ASan 不兼容，需要单独构建
4. 三者只进开发或测试产物：sanitizer 有可观的运行时与内存开销，进发布产物是事故
5. 常见组合 -fsanitize=address,undefined 已能拦住本书示例里的绝大多数错误
6. MSVC 只有 ASan 子集（/fsanitize=address），覆盖面明显小于 GCC/Clang

## 构建系统与目标定义

### CMake 的最小正确骨架

1. 声明最低版本、项目与语言，这三行是下限
2. 用 CMAKE_CXX_STANDARD 加 CMAKE_CXX_STANDARD_REQUIRED ON 固定标准；缺 REQUIRED 时会被静默降级
3. 编译选项挂在目标上（target_compile_options），挂全局会污染依赖且难以解释来源
4. 可执行输出目录要显式指定，否则不同生成器落点不同，文档里的运行路径就成了假话
5. 版本下限要选到真正使用特性的那一版；写一个很旧的下限等于允许读者用不支持的工具链尝试

### 为什么不能长期只教裸命令行

1. 单文件示例适合 g++ main.cpp，但它不表达依赖关系，读者进入多文件后仍要另学一套
2. 裸命令行的典型漏洞是没开警告与 sanitizer，越界与泄漏静默通过
3. 构建系统负责的是改一个文件时重编什么，这恰是初学者无法从单条命令里学到的
4. 建议顺序：先手写编译器命令理解发生了什么，再引入构建系统，最后解释增量为什么会出错

## 静态检查与格式化

### 分工

1. 排版（缩进、括号位置、列宽、include 排序）交给 clang-format，不做人工对齐
2. 命名、现代写法与惯用法交给 clang-tidy，它管的是这样写是否有更好的方式
3. 人的写法总会赢过口头约定，所以规则必须落到配置文件，而不是靠自觉
4. 配置文件必须有唯一出处，示例工程与文档都从它派生，否则读者复制到的是过期规则
5. 校验用非修改模式（--dry-run -Werror），让 CI 能失败而不是悄悄改写文件

### 检查子集

1. modernize-* 负责把 C-with-C++ 写法推向现代等价形式
2. cppcoreguidelines-* 负责所有权、生命周期与初始化等 Core Guidelines 约束
3. 全量开启会被噪音淹没，未定型的规则应显式关闭而不是被忽略

## 头文件与包含

### 自给自足

1. 每个头文件应能单独编译通过，不依赖先包含另一个的隐含约定
2. 不满足时的表现是换一种包含顺序就报错，这是最难定位的一类编译失败
3. 只包含真正需要的头文件，前向声明能切断的依赖就不要包含
4. 传递包含让编译时间随规模恶化，也把谁提供了这个名字变成不可读的问题
5. include guard 与 #pragma once 二选一，缺失会导致重定义

## 常见误区

### 配置层

1. 只在 -O0 下测试，发布 -O2 才暴露未定义行为与数据竞争
2. 认为能编译通过就是对的：不开警告会漏掉未初始化与签名不匹配
3. 把 sanitizer 编进发布产物
4. 在 MSVC 上使用 GCC 风格的标准开关
5. 依赖编译器默认标准，换机器后可用特性集合就变了

### 流程层

1. 用一次性成功输出证明配置正确，之后不再复核，配置文件漂移无人发现
2. 文档里写绝对路径或本机专属路径，读者复制即失败
3. 警告太多就整体关闭；正确做法是逐条处理或精确关闭单条规则
4. 把安装与验证合并成一条命令，失败时无法判断是没装上还是没生效
